> "报警 / 断线韧性 / 单 DLL 交付"，一共九章。全程只有一个例子：一台注塑机 IM-01（Modbus TCP 从站）。

# 第 1 章 快速上手：读第一个值

## 1.1 先从"你现在的处境"说起

你的注塑机上有一台 Modbus 从站，料筒温度存在输入寄存器地址 30，约定 ×0.1 就是摄氏度。
你想把它显示到自己的上位机界面上。如果从头写，你要做这些事：

```csharp
// 你自己写的话，大概是这个画风——开 socket、拼帧、算 CRC、解析回帧、处理超时重试……
var sock = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
// ……然后还有断线重连、多从站、字序、单位换算……业务还没写，光通讯就够忙一天
```

SuperSampler 想帮你的是：**你把"读哪些点、怎么解、多久读一次"写在配置里，把"拿到值以后干什么"
写在代码里，中间那摊脏活（调度、编解码、质量、重试）全部交给框架。**

这一章的目标只有一个：10 分钟内，从配置文件出发，把料筒温度打到屏幕上。

## 1.2 为什么该用"配置 + 回调"而不是自己写循环

1. **通讯不是你的业务**。轮询、分组、超时、断线重连是框架的职责（第 5、8 章展开），
   你只关心"值对不对、质量好不好"。
2. **值永远带着质量**。框架不给你"裸数据"，给的是"值 + 质量 + 时间戳"三元组（第 3 章），
   界面上该不该置灰、该不该判联锁，一眼可判。
3. **改点表不改代码**。现场加一个点位，改配置即可。没有点位元数据硬编码，
   就不会"加个点就要重新发版"。

## 1.3 先认识几个词（第 1 章精简版）

- **HostConfig（宿主配置）**：一份描述"链路 / 设备 / 点位 / 报警"的 XML，是整个框架的唯一输入。
- **Transport（链路）**：怎么连——TCP、串口 RTU 等。例子里是一条 TCP 链路指向 127.0.0.1:1502。
- **Device（设备）**：链路上的一个从站，用 **unitId（从站号）** 区分。例子里 unitId = 1。
- **PointSet（点表）**：一台设备读哪些点、怎么解，全在这张表里。
- **Point（点位）**：一个寄存器的命名视图：类型、字序、缩放、显示格式。
- **SamplerEngine（引擎）**：把配置变成运行时对象，负责调度与事件。
- **PointValue（点位值）**：`{值, 质量, 时间戳}` 三元组，是框架给宿主的一切数据的形状。

> 术语完整对照见附录 B。现在只需要"大概知道"，用到哪章再深入哪章。

## 1.4 动手做：10 分钟读第一个值

### 第 1 步：准备玩具从站（或你的真设备）


### 第 2 步：写最小 HostConfig 配置，存成 `im01.xml`

```xml
<?xml version="1.0" encoding="utf-8"?>
<HostConfig schemaVersion="3.0">
  <Global language="zh_CN" nullText="--" swap="word">
    <Polling defaultIntervalMs="1000" requestTimeoutMs="1000"/>
  </Global>
  <Transports>
    <!-- 怎么连：一条 TCP 链路指向玩具从站 -->
    <Transport id="im01-net" variant="tcp" enabled="true"
               host="127.0.0.1" port="1502"
               connectTimeoutMs="2000" requestTimeoutMs="1000"/>
  </Transports>
  <Devices>
    <!-- 连哪台：unitId=1 的从站，读 IM01_Points 这张点表 -->
    <Device id="IM-01" name="1号注塑机" enabled="true"
            transport="im01-net" unitId="1" pointSet="IM01_Points"/>
  </Devices>
  <PointSets>
    <PointSet id="IM01_Points">
      <Defaults area="input" dataType="uint16" swap="none"/>
      <Points>
        <!-- 读什么：地址 30，int16，×0.1 就是摄氏度 -->
        <Point id="barrel.temp" name="料筒1段温度" address="30" dataType="int16">
          <Scale factor="0.1"/>
          <Format decimals="1" suffix=" ℃"/>
        </Point>
      </Points>
    </PointSet>
  </PointSets>
</HostConfig>
```

这段配置的意思一句话：**TCP 连上 127.0.0.1:1502，从 unitId=1 的从站、输入寄存器地址 30 读一个
int16，×0.1 后显示成"220.0 ℃"，每秒轮询一次。** 每个字段都有行为，这就是"声明即生效"
（第 2 章细讲）。

### 第 3 步：写宿主代码，存成 `Program.cs`

```csharp
using System;
using SuperSampler.Abstractions.Events;
using SuperSampler.Core.Config;
using SuperSampler.Core.Runtime;

class Program
{
    static void Main()
    {
        // ① 加载并校验配置（两阶段，一次报全所有矛盾，见第 2 章）
        var config = SamplerConfigLoader.LoadFromXml(@"D:\cfg\im01.xml");

        // ② 创建引擎（配置没过校验时根本到不了这一行）
        using var engine = new SamplerEngine(config);

        // ③ 先订阅、后 Start：引擎一启动就发事件，晚订阅会漏掉第一批
        using var sub = engine.Bus.Subscribe<PointValueChangedEvent>(env =>
            Console.WriteLine($"[值变化] {env.Body.DeviceId}/{env.Body.PointId} = {env.Body.Value}"));

        // ④ 启动：按配置的 intervalMs 开始轮询
        engine.Start();

        // ⑤ 等一两拍再读：轮询是异步的，Start 后立刻读可能还没读到第一笔
        System.Threading.Thread.Sleep(1500);

        // ⑥ 读实时缓存（只读缓存、不发通讯，可高频调用）
        var pv = engine.GetValueDetail("IM-01", "barrel.temp");
        Console.WriteLine($"料筒温度 = {pv.Value}℃，质量 = {pv.Quality}");

        // ⑦ 停止（Stop 后不可再 Start，需要重跑就重建引擎，见第 4 章）
        engine.Stop();
    }
}
```

### 第 4 步：编译运行

```bash
# 接入方式两种：项目引用（开发/跟源码）或单 DLL（交付/黑盒），详见仓库 README「接入方式」
dotnet build 你的宿主工程.csproj
dotnet run   你的宿主工程.csproj

# 期望输出（数值会随玩具从站的漂移略有不同）：
# [值变化] IM-01/barrel.temp = 220.0 ℃
# 料筒温度 = 220.0℃，质量 = Good
```

> 注意第 3 步里 `Thread.Sleep(1500)` 的原因：引擎 Start 后轮询是异步的，立刻 `GetValueDetail`
> 可能还没读到第一笔（质量不是 Good）。等一两拍再读，或者干脆靠订阅事件拿值。

## 1.5 想深一层（可选）：这一章背后发生了什么

> 懂这节更好，不懂也不影响你用——这是心智模型，不是实现细节。

- **声明即生效**：你在配置里写的每个字段都有行为。`intervalMs="1000"` 就是每秒轮询一次；
  `Scale factor="0.1"` 就是读到的 2200 显示成 220.0。配置不是"给界面看的花架子"，它是行为本身。
- **两阶段加载**：`LoadFromXml` 先解析、再全量校验，所有矛盾一次收集（第 2 章讲怎么利用它）。
- **先订阅后 Start**：引擎一启动就发事件，晚订阅会漏掉第一批（可能就在启动后几毫秒）。

## 1.6 常见坑与最佳实践

🔴 反模式：先 `Start()` 再 `Subscribe()`。第一批值变化事件在你订阅之前就发出去了，界面会缺一块。
✅ 正确写法：订阅永远在 Start 之前（引擎构造之后、Start 之前）。

🔴 反模式：读值用 `GetValue()` 的返回串做逻辑判断（比如"温度是不是 220"）。
✅ 正确写法：逻辑判断用 `GetValueDetail()` 的 `PointValue`，先看质量再看值（第 3 章详述）。

🔴 反模式：deviceId / pointId 写错，然后吞掉异常。`GetValue` / `GetValueDetail` 对未知 id 抛
`KeyNotFoundException`。
✅ 正确写法：让异常尽早炸出来；id 对照本章开头那张事实表检查。

## 1.7 小结

- 接入四步：写 HostConfig → `LoadFromXml` → `new SamplerEngine` → **先订阅后 Start**。
- 读值三兄弟：`GetValue`（显示串）/ `GetValueDetail`（三元组）/ `GetValueAge`（新鲜度），
  都只读缓存、不发通讯。
- 值永远带质量：非 Good 时 `GetValue` 返回 `nullText`，别把旧值当好值。
- 停止：`engine.Stop()`；Stop 后不可再 Start，要重跑就重建引擎（第 4 章详述）。

# 第 2 章 配置详解：链路、设备、点位

## 2.1 从"一次看到 6 个报错"说起

你照着第 1 章抄，想把 IM-01 的报警、报警码、模具温度、目标产量全加进去。改完配置一加载：

```
ConfigValidationException: 6 个错误
  · PointSet[IM01_Points]: Point[id=alarm] 的 dataType 'bool' 与 area 'discrete' 不匹配？
  · PointSet[IM01_Points]: Point[id=barrel.set] 的 area 'holding' 未继承默认 area 'input'？
  · Devices: Device[id=IM-01] 的 pointSet 'IM01_Points2' 不存在？
  · ……（示意，别照抄）
```

别慌。这不是"配置烂"，而是框架在**一次把所有矛盾都告诉你**——每条都带定位
（哪张点表、哪个点位、哪个属性、为什么）。你只需要从上到下一一修好，再加载一次就过了。
这一章就是帮你把每个节点每个属性看懂，少走弯路。

## 2.2 为什么配置这么"啰嗦"——三个行为层理由

1. **配置就是行为**：没有代码生成的点表，没有硬编码的寄存器表。读哪些、怎么解、多久读一次，
   全部由配置驱动。改配置 = 改行为。
2. **校验替你挡错误**：地址越界、类型和长度不匹配、报警限值大小关系反了……加载期一次报全，
   而不是运行到一半才发现"没有值"。
3. **声明即生效**：每个字段都有消费方（除了明确标注"未实现"的，见 2.6）。写
   `requestTimeoutMs="1000"` 就是 1 秒超时；写 `verify="true"` 就是写后回读校验。

## 2.3 先认识配置的骨架（术语 + 节点地图）

一份 HostConfig 的推荐书写顺序（根节点）：

```
HostConfig (schemaVersion, unsupportedPolicy)
├── Global        全局默认值：语言 / nullText / 轮询 / 重试 / 退避 / 分组上限……
├── Transports    链路：怎么连（TCP / 串口，端口，超时）
├── Devices       设备：连哪台（transport + unitId + pointSet）
├── PointSets     点表：读什么、怎么解
└── AlarmClasses  报警等级（第 7 章用）
```

三个关键概念先分清：

- **Transports（链路）管"怎么连"**：协议、IP/端口（或串口号）、连接超时、请求超时。
- **Devices（设备）管"连哪台"**：挂在哪条链路上（`transport`）、从站号（`unitId`）、读哪张表（`pointSet`）。
- **PointSets / Point（点表与点位）管"读什么、怎么解"**：地址、数据类型、字序、缩放、轮询间隔、读写权限。

> 一句话：**链路管怎么连，设备管连哪台，点位管读什么怎么解。** 三层各管一摊，别混。

## 2.4 动手做：把 IM-01 全部点位写进配置

### 2.4.1 完整配置（IM-01 的六个点都在里面）

```xml
<?xml version="1.0" encoding="utf-8"?>
<HostConfig schemaVersion="3.0">
  <Global language="zh_CN" fallbackLanguage="en_US" nullText="--" swap="word">
    <Polling defaultIntervalMs="1000" requestTimeoutMs="1000"/>
  </Global>

  <Transports>
    <!-- 链路：怎么连。variant = tcp | rtuovertcp | rtu（udp/ascii 未实现，写了告警） -->
    <Transport id="im01-net" variant="tcp" host="127.0.0.1" port="1502"
               connectTimeoutMs="2000" requestTimeoutMs="1000"/>
  </Transports>

  <Devices>
    <!-- 设备：连哪台。transport 必填；unitId 是整数（别写 "01"）；pointSet 必填 -->
    <Device id="IM-01" name="1号注塑机" transport="im01-net" unitId="1" pointSet="IM01_Points"/>
  </Devices>

  <PointSets>
    <PointSet id="IM01_Points">
      <!-- Defaults：没显式写的点位从这里继承（area/dataType/swap/access） -->
      <Defaults area="input" dataType="uint16" swap="none"/>

      <Points>
        <!-- 1x 离散输入：报警（bool） -->
        <Point id="alarm" name="报警" area="discrete" address="3" dataType="bool"/>

        <!-- 3x 输入寄存器：报警码（整字枚举，用 Format/Map 映射成中文显示） -->
        <Point id="alarm.code" name="报警码" address="1" dataType="uint16">
          <Format>
            <Map>
              <Item key="0">无</Item>
              <Item key="1">油温过高</Item>
              <Item key="2">模具超温</Item>
              <Item key="4">射胶异常</Item>
            </Map>
          </Format>
        </Point>

        <!-- 3x 输入寄存器：料筒1段温度（int16 ×0.1），温度想读密一点，intervalMs="500" -->
        <Point id="barrel.temp" name="料筒1段温度" address="30" dataType="int16" intervalMs="500">
          <Scale factor="0.1"/>
          <Format decimals="1" suffix=" ℃"/>
        </Point>

        <!-- 3x 输入寄存器：模具实际温度（int16 ×0.1） -->
        <Point id="mold.temp" name="模具实际温度" address="35" dataType="int16" intervalMs="500">
          <Scale factor="0.1"/>
          <Format decimals="1" suffix=" ℃"/>
        </Point>

        <!-- 4x 保持寄存器：目标产量（可写；Write 声明范围校验 + 写后回读校验） -->
        <Point id="target.output" name="目标产量" area="holding" address="1"
               dataType="uint16" access="readwrite">
          <Write min="0" max="9999" verify="true"/>
        </Point>

        <!-- 4x 保持寄存器：料筒1段设定（可写，实际温度向它靠拢） -->
        <Point id="barrel.set" name="料筒1段设定" area="holding" address="2"
               dataType="int16" access="readwrite" intervalMs="500">
          <Scale factor="0.1"/>
          <Format decimals="1" suffix=" ℃"/>
          <Write min="0" max="400" verify="true"/>
        </Point>
      </Points>
    </PointSet>
  </PointSets>
</HostConfig>
```

存成 `im01-full.xml`，替换第 1 章 `Program.cs` 里的路径再跑一次，屏幕应该多出五个点的值。

### 2.4.2 逐节点要点

- **`<Global>`**：全局兜底。`nullText`（坏值占位，默认 `--`）、`swap`（字序兜底，默认 `word`）、
  `<Polling defaultIntervalMs requestTimeoutMs>`（点位未写间隔时的兜底，默认 1000/1000）。
- **`<Transport>`**：`variant="tcp"` 时看 `host` / `port`（默认 502）；串口用 `variant="rtu"`
  加 `portName` / `baudRate` / `parity` 等（见 9.2.4 多从站/串口）。`requestTimeoutMs` 默认 1000。
- **`<Device>`**：`transport` 与 `pointSet` 必填；`unitId` 默认 1；`enabled="false"` 完全不轮询。
- **`<PointSet>` 里四段平级**：`Defaults`（继承默认）、`Blocks`（块读，第 5 章）、`Points`（普通点位）、
  `Calculated`（计算点，第 3 章提过）。
- **`<Point>`**：`area` / `address`（0 基）/ `dataType` / `swap` / `access` / `intervalMs` / `mode`；
  子元素 `<Scale>`（缩放）、`<Format>`（显示）、`<Write>`（写约束）、`<Alarm>`（第 7 章）、
  `<Script>` / `<String>` / `<Bits>` / `<Slices>`（第 3、9 章）。
- **继承链**：`Point > Block（显式）> Defaults > Device > Global`，就近优先、只取一份。

### 2.4.3 加载这段配置（顺便看报错长什么样）

```csharp
using SuperSampler.Core.Config;

try
{
    var cfg = SamplerConfigLoader.LoadFromXml(@"D:\cfg\im01-full.xml");
    Console.WriteLine("加载通过，零错误。");
    // cfg.Warnings 里是"可接受但不推荐"的点，打印出来看一眼，别无视
    foreach (var w in cfg.Warnings) Console.WriteLine("  警告: " + w);
}
catch (ConfigValidationException ex)
{
    // Errors 是这一次加载收集到的全部硬错误，一次修完
    foreach (var e in ex.Errors) Console.WriteLine("  · " + e);
    throw; // 配置不过就拒绝启动，别带病运行
}
```

## 2.5 想深一层（可选）：两阶段加载与"一次报全"

> 不懂也能用。这是心智模型。

加载分两个阶段：① 解析 XML + 全量语义校验，把**所有**矛盾收集成一个错误列表——不会遇到第一个错误
就停，解析期碰到的非法数值也会转成带定位的错误继续跑后面的规则；② 零错误才产出 `SamplerConfiguration`。
之后 `new SamplerEngine(config)` 会强制检查"这份配置通过校验没有"——手工拼一个没校验的配置对象是
**无法实例化引擎**的（抛 `InvalidOperationException`）。

所以"一次报全"不是巧合：它刻意收集全部错误，让你一次性修完，省得改了 A 又报 B、来回七八趟。

## 2.6 常见坑与最佳实践

🔴 反模式：`<Defaults area="input">` 下面所有点都继承 `input`（只读区），想写"目标产量"却忘了给
那个点写 `area="holding"`。加载报"只读区不得声明可写"。
✅ 正确写法：不同数据区的点，显式写 `area`；别全靠继承。

🔴 反模式：抄到未实现段（`Storage` / `Ui` / `Users` / `Commands` / `Diagnostics/Trace` 等），
写上去"没反应"。
✅ 正确写法：这些段当前**不产生行为**，写了会按 `unsupportedPolicy`（默认 `warn`）记入 Warnings。
完整清单见第 9 章 9.1。

🔴 反模式：`intervalMs="10"`（小于 50ms 调度节拍）。加载直接报错。
✅ 正确写法：间隔 ≥ 50ms；默认 1000ms（`Global/Polling@defaultIntervalMs`）。

🔴 反模式：把 `unitId` 写成 `"01"`（字符串）。unitId 是整数。
✅ 正确写法：`unitId="1"`。

🔴 反模式：设备 id / 点 id 前后不一致，配置里 `IM-01`、代码里 `IM01`，运行期抛
`KeyNotFoundException` 才暴露。
✅ 正确写法：id 是一等公民，配置和代码对照着写；`deviceId/pointId` 是门面寻址主键（第 3 章 3.3）。

## 2.7 小结

- 三层分工：Transports 管怎么连、Devices 管连哪台、PointSets/Point 管读什么怎么解。
- 两阶段加载一次报全所有矛盾；零错误才可能实例化引擎。
- 继承链：Point > Block（显式）> Defaults > Device > Global；就近优先、只取一份。
- 未实现段写了进 Warnings，别按它们的功能期待行为。
- 校验规则全表在 `docs/配置XML说明.md` 第 16 节，报错看不懂就翻它。

# 第 3 章 值、类型与解码

## 3.1 从"为什么显示 2200 而不是 220.0"说起

第 1 章的例子能跑，但你顺手把 `<Scale factor="0.1"/>` 删了，屏幕上的料筒温度立刻变成 2200：

```csharp
// 删掉 Scale 之后……
var pv = engine.GetValueDetail("IM-01", "barrel.temp");
Console.WriteLine(pv.Value);   // 输出 2200，不是 220.0——设备没坏，寄存器里存的就是整数 2200
```

不是设备坏了——设备里的寄存器存的就是整数 2200，只是它约定"×0.1 才是摄氏度"。
更麻烦的情况：你接了个 32 位浮点压力，读出来是个天文数字；或者读到一堆乱码。
这些十有八九是**类型 / 字序 / 缩放**没配对。这一章就把"从寄存器到工程值"这条链彻底讲清。

## 3.2 为什么框架要搞"值 + 质量 + 时间戳"——行为层理由

1. **原始寄存器 ≠ 工程值**。2200 到底是温度还是"2200 个什么"，要靠配置里的类型 + 缩放来解释。
2. **读数可能不可信**。超时、解码失败、设备离线，值就是假的。框架给每个值打质量标签，
   界面据此置灰，绝不把假数据当好数据显示。
3. **新鲜度由宿主判断**。框架给你"距上次成功采集多久"（`GetValueAge`），"多久算陈旧"
   （温度 1s、配方 1h）是工艺，阈值由宿主定。

## 3.3 先认识术语

- **PointValue（点位值）**：`{值(Value), 质量(Quality), 时间戳(Timestamp)}` 三元组，
  外加 `Reason`（坏值原因，i18n key，宿主用来做界面提示）。
- **质量四态（PointQuality）**：`Good`（可信）/ `Uncertain`（可疑，可能还能用，需谨慎）/
  `Bad`（不可用）/ `Offline`（链路或设备离线）。
- **dataType（数据类型）**：13 种——`bool / int16 / uint16 / int32 / uint32 / int64 / uint64 /
  float32 / float64 / string / bcd / datetime / raw`。
- **swap（字序）**：4 种——`none(ABCD) / byte(BADC) / word(CDAB) / word_byte(DCBA)`，多字值才受影响。
- **Scale（缩放）**：`factor × raw + offset`，或双点映射 `rawLow/rawHigh → scaledLow/scaledHigh`，
  可配 `<Clamp>` 钳位。
- **GetValue / GetValueDetail / GetValueAge**：显示串 / 三元组 / 新鲜度（第 1 章已见）。

## 3.4 动手做：把 IM-01 的类型和缩放配对

### 3.4.1 常用的几种 dataType

| dataType | 字长 | 典型用途 | 取值（工程值） |
|---|---|---|---|
| `bool` | 1 位（或整字取位） | 报警、启停标志 | true / false |
| `uint16` | 1 寄存器 | 计数、产量、报警码 | 0..65535 |
| `int16` | 1 寄存器 | 带符号温度 | -32768..32767 |
| `uint32` | 2 寄存器 | 累计值 | 0..4_294_967_295 |
| `float32` | 2 寄存器 | 压力、流量 | 浮点 |
| `string` | 按 `length` | 配方名、批次号 | 字符串 |

> 其余 `int32 / int64 / uint64 / float64 / bcd / datetime / raw` 不常碰：`bcd` 是 BCD 编码数字、
> `datetime` 是 PLC 时间戳（plc6/plc4/unixsec/unixms）、`raw` 是原始字节。用到再查
> `docs/配置XML说明.md` 的 `dataType` 与 `<Bcd>` / `<DateTime>` 小节。

### 3.4.2 一个点覆盖三种解码：温度、压力、配方

```xml
<!-- 第 2 章配置的基础上，往 IM01_Points 里加这几个点演示解码 -->

<!-- int16 ×0.1：raw 2200 → 220.0 ℃ -->
<Point id="barrel.temp" name="料筒1段温度" address="30" dataType="int16">
  <Scale factor="0.1"/>
  <Format decimals="1" suffix=" ℃"/>
</Point>

<!-- float32：玩具从站在地址 10 放了一个 22.0 的大端浮点（swap="none"） -->
<Point id="pressure" name="射胶压力" area="input" address="10" dataType="float32" swap="none">
  <Format decimals="2" suffix=" MPa"/>
</Point>

<!-- string：玩具从站在地址 10 放了 12 字节 ASCII "RX-88" -->
<Point id="recipe" name="配方名" area="holding" address="10" dataType="string" length="12">
  <String encoding="ascii" trimNull="true"/>
</Point>
```

> 为什么 `pressure` 要单独写 `swap="none"`？因为 Global 默认 `swap="word"`（CDAB 字交换），
> 而玩具从站按标准大端存的（高字在前）。多字值不配 swap 就按错字序解，读出来的浮点自然是天文数字。
> 真设备按手册查：国内设备常见 `word`，标准大端用 `none`。

### 3.4.3 读值：先看质量，再取工程值

```csharp
using SuperSampler.Abstractions.Values;

// ① 要判断 / 联锁：拿三元组，先看质量再看值
PointValue pv = engine.GetValueDetail("IM-01", "barrel.temp");
if (pv.IsGood && pv.TryGetValue<double>(out var temp))
    Console.WriteLine($"料筒温度 = {temp} ℃");      // TryGetValue 类型不符返回 false，不抛异常
else
    Console.WriteLine($"质量 {pv.Quality}，原因 {pv.Reason}");

// ② 要给人看：直接要显示串（缩放/枚举/前后缀/i18n 都做好了）
string text = engine.GetValue("IM-01", "barrel.temp");  // 质量非 Good 时返回 nullText "--"

// ③ 数据新鲜度：宿主自己定"多久算陈旧"
TimeSpan? age = engine.GetValueAge("IM-01", "barrel.temp");
if (age.HasValue && age.Value > TimeSpan.FromSeconds(5))
    ShowStaleBadge();   // 超过 5 秒没刷新，标一下
```

### 3.4.4 质量四态与常见原因码

| 质量 | 含义 | 常见 Reason（i18n key） |
|---|---|---|
| `Good` | 数据可信 | `null` |
| `Uncertain` | 可疑，值可能还能用 | `ss.reason.nan` / `ss.reason.infinite`（换算出 NaN/无穷） |
| `Bad` | 不可用 | `ss.reason.decode`（解码失败）/ `ss.reason.shortFrame` / `ss.reason.scriptTimeout` 等 |
| `Offline` | 链路或设备离线 | `ss.quality.offline`（通讯失败、退避中） |

> 界面提示用 `Reason` 这个稳定 key，别自己猜原因、别依赖具体语言文案（本地化由宿主做）。

## 3.5 想深一层（可选）：解码管道

> 心智模型。从寄存器到屏幕，每个值都走这条路：

```
寄存器 → 字序(swap) → 类型解释 → [原始数值]
   → Scale(缩放+钳位) →【工程值】→ Format(decimals/Map/前后缀) →【显示文本】
```

- **报警、写值、历史只消费【工程值】**；【显示文本】只给界面（`GetValue`）。这就是为什么第 2 章里
  `Write min="0" max="400"` 用的是工程值（℃），不是 raw。
- **位点 / 位域（`bit` / `bitRange`）直接从寄存器取位，不经过 swap**——取位与字序无关。
- **有 `<Script>` 时脚本返回值即工程值，不再叠加 Scale**（第 9 章 9.2.1 会讲脚本）。

## 3.6 常见坑与最佳实践

🔴 反模式：多字值（float32 / uint32）忘配 swap，读数像天文数字。
✅ 正确写法：按设备手册查字序。国内设备常见 `swap="word"`（也是 Global 默认）；标准大端用 `none`。
不确定就用 `RawReadAsync` 读出原始寄存器比对（第 8 章调试门面）。

🔴 反模式：用 `GetValue()` 的返回串做逻辑判断。
✅ 正确写法：逻辑一律 `GetValueDetail()` + `IsGood` + `TryGetValue<T>()`；字符串只是给人看的。

🔴 反模式：把换算出 NaN / 无穷当正常值显示。
✅ 正确写法：NaN / 无穷会降级为 `Uncertain` 并带 `ss.reason.nan` / `ss.reason.infinite`，
按质量分支处理（第 1 章 1.6 说过：先看质量再看值）。

🔴 反模式：string 点位不写 `length`。框架不知道读几个寄存器，解码对不上。
✅ 正确写法：`length` 按设备手册（每个寄存器 2 个 ASCII 字符）；必要时配
`<String encoding trimNull left/>` 处理补齐与裁剪。

## 3.7 小结

- 13 种 dataType、4 种 swap、Scale 缩放 + Clamp 钳位；多字值 swap 一定要按手册配。
- 值永远伴随质量与时间戳：先 `IsGood`，再用 `TryGetValue<T>()` 安全取类型值。
- 质量四态 Good / Uncertain / Bad / Offline，坏值原因用 `Reason`（i18n key）提示，别自己猜。
- 解码管道：寄存器 → swap → 类型 → Scale → 工程值 → Format → 显示文本；
  报警和写值只看工程值，显示文本只给界面。

# 第 4 章 引擎生命周期与读写

## 4.1 从"写了 150，设备不认"说起

你在界面上给"料筒 1 段设定"填了 150，调用写接口，结果返回 `Rejected`；你又试着给"目标产量"填
999999，也失败；最坑的是有一次写了半天没响应，返回 `Indeterminate`——值到底写没写进去？

```csharp
var result = await engine.SetValueAsync("IM-01", "barrel.set", 150.0, user);
Console.WriteLine(result.Outcome);   // Rejected? Indeterminate? 还是你以为的 Succeeded?
```

这一章把"引擎怎么活、怎么写值"讲透：先把生命周期这条主线立起来，再讲写值的四态结果怎么处置。

## 4.2 为什么生命周期"这么严格"——行为层理由

1. **未过校验的配置不允许实例化**。你永远不会在运行时才发现"配置错了"，加载期就把你拦下了
   （第 2 章 2.5 讲过这条兜底）。
2. **先订阅后 Start 是硬要求**。引擎一启动就发事件，晚订阅会漏第一批（第 1 章 1.6 的坑）。
3. **Stop 后不可再 Start**。引擎是一次性对象，防止你把一个"已释放调度器"的引擎当正常引擎用。
4. **写值不静默失败**。业务失败用结果对象表达（四态），不抛异常、不假装成功——
   写没写进去，你一定知道。

## 4.3 先认识术语

- **LoadFromXml（加载）**：读配置 + 两阶段校验，产出 `SamplerConfiguration`。
- **ConfigValidationException（配置校验异常）**：`Errors`（全部硬错误）/ `Warnings`（可接受但不推荐）。
- **SamplerEngine（引擎）**：实现门面接口 `IDeviceManager` / `IModbusDebugTool`，同时是 `IDisposable`。
- **Start / Stop / Dispose**：启动调度 / 停止调度 / 释放资源。
- **WriteOutcome（写结果四态）**：`Succeeded` / `Failed` / `Indeterminate` / `Rejected`。
- **ActingUser（操作者）**：宿主认证后的用户（`Name`, `RoleId`），框架只用来做**审计记账**，
  不做角色授权——授权是宿主的事。

## 4.4 动手做：完整生命周期 + 写值

### 4.4.1 生命周期主流程

```csharp
using SuperSampler.Abstractions.Events;
using SuperSampler.Core.Config;
using SuperSampler.Core.Runtime;

// ① 加载（一次报全所有矛盾；不过就抛 ConfigValidationException）
var config = SamplerConfigLoader.LoadFromXml(@"D:\cfg\im01-full.xml");

// ② 构造引擎（未通过校验的配置到不了这一行）
using var engine = new SamplerEngine(config);

// ③ 先订阅
using var sub = engine.Bus.Subscribe<PointValueChangedEvent>(env =>
    Console.WriteLine($"[值变化] {env.Body.DeviceId}/{env.Body.PointId} = {env.Body.Value}"));

// ④ 启动：按配置的 intervalMs 开始轮询所有使能设备
engine.Start();

// ⑤ 日常读写……（见 4.4.2）

// ⑥ 停止 + 释放
engine.Stop();
// using 块结束自动调用 Dispose；即使忘了 Stop，Dispose 也会安全收尾
```

生命周期边界（务必遵守）：

- **先订阅后 Start**：硬性要求，理由见 4.2。
- **Stop 后不可再 Start**：重新 Start 不受支持；宿主如需重新运行，请**重建一个 `SamplerEngine`**
  （配置对象可复用）。
- **引擎长期存活**：在应用启动时创建、退出时销毁，不要为单次读取反复创建/销毁引擎。

### 4.4.2 写值：四态结果与处置

```csharp
using SuperSampler.Abstractions.Facade;   // ActingUser / WriteOutcome 等门面契约

// 带操作者身份写（接入宿主登录后请用这个重载；框架只记审计，不拦权限）
var user = new ActingUser("zhangsan", "Operator");
var result = await engine.SetValueAsync("IM-01", "barrel.set", 180.0, user);

switch (result.Outcome)
{
    case WriteOutcome.Succeeded:
        if (result.VerifyMismatch)
            ShowNotice($"实际值 {result.Readback?.Value} 与写入值不同（设备可能钳位，别自动重试）");
        break;
    case WriteOutcome.Failed:
        break; // 明确失败：设备拒绝或通讯错误，可安全重试
    case WriteOutcome.Indeterminate:
        // 写入可能已生效！绝不自动重试，先回读现场值确认再决定下一步
        var check = await engine.GetValueDetail("IM-01", "barrel.set");
        break;
    case WriteOutcome.Rejected:
        break; // 未发出任何通讯（范围/可写性校验没过），提示操作者，重试也没用
}
```

四态各自的含义与处置：

| Outcome | 含义 | 处置 |
|---|---|---|
| `Succeeded` | 写入成功（`verify=true` 时已通过回读校验） | 正常；若 `VerifyMismatch` 置位，提示实际值 |
| `Failed` | 明确失败：设备拒绝或通讯错误 | **可安全重试**（重试无副作用） |
| `Indeterminate` | 不确定：超时或应答异常，写入**可能已生效** | **绝不自动重试**，须回读确认 |
| `Rejected` | 被拒绝：范围 / 类型容量 / 可写区校验没过，**未发出任何通讯** | 提示操作者，先改条件 |

> **`VerifyMismatch`**：点位配了 `verify="true"` 且通讯成功时，框架会回读校验。如果设备应答成功、
> 但回读值与写入值不一致（典型如设备自行钳位到量程内），结果置位 `VerifyMismatch`，但 Outcome 仍是
> `Succeeded`——因为通讯确实成功。宿主应提示"实际值 X 与写入值不同"，并且**不要自动重试**。

### 4.4.3 类型强转建议

写值请按点位 `dataType` 给对应 .NET 类型：数值点给 `int` / `long` / `double`，字符串点给 `string`。
把界面输入原样以字符串传给数值点，框架可能做隐式转换——但**字符串 → 数值会丢精度或失败**。
最好在宿主侧把界面输入按 `dataType` 强转成数值后再写入：

```csharp
// 界面输入是 string "180.0"，先按点位类型转好再写，别把字符串直接丢给数值点
if (double.TryParse(input.Text, out var setpoint))
    await engine.SetValueAsync("IM-01", "barrel.set", setpoint, user);
```

## 4.5 想深一层（可选）：写管道

> 心智模型。写一个值要过五关，任何一关不过都不会把假数据发出去：

```
可写性(access) → 数据区 → 范围(Write@min/max) → 类型容量 → 编码 → 下发 →（verify=true）回读校验
```

- `Rejected` 是前几关没过：**没发出任何通讯**，重试无意义，先改条件。
- `Indeterminate` 是"发出去了但不知道结果"：通讯层的天然不确定性，**绝不自动重试**。
- 框架的写请求**恒不自动重试**（与 `Retry@count` 无关），重不重试、怎么重试是宿主决策。
- 范围校验用的是 `Write@min` / `Write@max`（工程值，第 3 章 3.5 说过报警和写值只看工程值）。

## 4.6 常见坑与最佳实践

🔴 反模式：把界面输入原样（string）传给数值点。
✅ 正确写法：按 dataType 强转成 int / long / double 再写；字符串 → 数值会丢精度或失败（见 4.4.3）。

🔴 反模式：`Indeterminate` 之后自动重试 N 次。
✅ 正确写法：先 `GetValueDetail` 回读确认是否已生效；自动重试可能造成重复写入（比如重复启动）。

🔴 反模式：`Stop()` 之后再 `Start()`，以为能恢复。
✅ 正确写法：Stop 后不可再 Start（是空操作），要重跑就重建 `SamplerEngine`（配置对象可复用）。

🔴 反模式：设定值点位忘配 `verify="true"`，写"成功了"但设备把值钳位到量程内，界面显示 180 实际 120。
✅ 正确写法：设定值类点位配 `<Write verify="true"/>`；`VerifyMismatch` 置位时提示"实际值 X 与写入值
不同"，别自动重试（重试改变不了设备的钳位行为）。

## 4.7 小结

- 生命周期一条线：LoadFromXml → new SamplerEngine → 先订阅 → Start → 读写 → Stop → Dispose。
- 配置未过校验无法实例化引擎；Stop 后不可再 Start，重跑重建引擎（配置对象可复用）。
- 写四态：Succeeded / Failed / Indeterminate / Rejected；Indeterminate 绝不自动重试，
  Rejected 先改条件。
- `verify="true"` 写后回读校验；`VerifyMismatch` 只提示、不重试。
- 写审计：所有写操作（无论成败）都发 `PointWrittenEvent`（第 6 章细讲怎么接）。

# 第 5 章 调度与性能

## 5.1 从"50 个点把链路打爆了"说起

你照着前面章节给 IM-01 加了 50 个点，每个点都写 `intervalMs="100"`：

```xml
<!-- 50 个点 × 每秒 10 次 = 每秒 500 次请求，链路直接被塞满 -->
<Point id="p01" address="0" dataType="uint16" intervalMs="100"/>
<Point id="p02" address="1" dataType="uint16" intervalMs="100"/>
<!-- …… -->
```

结果链路被请求塞满，同链路的其它设备读得越来越慢，CPU 也高了。

原因可能不是"点太多"，而是**散点被当成一次一个请求在读**。这一章讲框架怎么调度、怎么自动合并，
以及你怎么用 `intervalMs` / `mode` / `Block` 控制节奏。

## 5.2 为什么不用你操心"合并"——行为层理由

1. **散点自动分组**：同一设备、同一从站（unitId）、同一数据区，地址连续的点自动合并成一次请求读回。
2. **上限自动切分**：一次请求有上限（寄存器 125 / 位 2000），超了自动切成多次请求、同一拍读完。
3. **块读显式声明**：想"一次读一整段"，用 `<Block>` 明确告诉框架。
4. **节奏写在点自己身上**：`intervalMs` 决定多久读一次，`mode` 决定什么时候读（周期 / 手动 / 只读一次）。

## 5.3 先认识术语

- **intervalMs（轮询间隔）**：毫秒，≥50（调度节拍）；未写取 `Global/Polling@defaultIntervalMs`（1000）。
- **mode（读取模式）**：`auto`（默认，周期读）/ `onDemand`（不轮询，只手动触发）/
  `once`（启动后读一次，直到成功）。
- **自动分组（automatic grouping）**：把连续地址的散点合并成一次 Modbus 请求，是默认行为、无需开关。
- **Block（块）**：显式声明的一段地址窗口 + 该段的间隔与模式。
- **分桶（bucketing）**：同设备、相同 `intervalMs` 的点/块走同一节拍（一个桶一轮），不同间隔各走各的。

## 5.4 动手做：用 IM-01 把节奏配起来

### 例 1：温度读密一点，其它点正常

```xml
<!-- 温度 500ms 一轮，其它点走全局默认 1000ms -->
<Point id="barrel.temp" name="料筒1段温度" address="30" dataType="int16" intervalMs="500">
  <Scale factor="0.1"/>
  <Format decimals="1" suffix=" ℃"/>
</Point>

<Point id="alarm.code" name="报警码" address="1" dataType="uint16"/>
```

同一个设备上，500ms 的点和 1000ms 的点各走各的节拍，互不干扰。

### 例 2：用 Block 一次读一整段（保持寄存器 1..2 正好连续）

```xml
<Blocks>
  <!-- 块读：一次请求读 start=1 起的 2 个寄存器；块内点位地址必须连续 -->
  <Block id="im01.holding" area="holding" start="1" count="2" intervalMs="1000">
    <Point id="target.output" name="目标产量" address="1" dataType="uint16" access="readwrite">
      <Write min="0" max="9999" verify="true"/>
    </Point>
    <Point id="barrel.set" name="料筒1段设定" address="2" dataType="int16" access="readwrite">
      <Scale factor="0.1"/>
      <Write min="0" max="400" verify="true"/>
    </Point>
  </Block>
</Blocks>
```

块的四条铁律（校验不过加载即报错）：

- 块内点位写**绝对地址**，必须落在 `[start, start+count)`；
- 块内点位不得覆盖 `area / unitId / intervalMs / mode`（决定"怎么读、多久读"，统一由块说了算）；
- 块内点位地址必须**连续**（空洞不得超过 `Scheduler@ignoreGap`，默认 0 = 严格连续；
  窗口尾部可以留白，点之间不许留洞）；
- `count` 不得超过地址组上限（寄存器 125 / 位 2000）——块是"显式声明的一次请求"，不能超。

### 例 3：onDemand——不进轮询，只等手动触发

```xml
<!-- onDemand 完全不参与轮询，只靠手动触发驱动 -->
<Point id="batch.weight" name="批次重量" address="60" dataType="uint16" mode="onDemand"/>
```

```csharp
// 手动触发单个 onDemand 点（结果写入实时缓存并返回）
var v = await engine.TriggerReadAsync("IM-01", "batch.weight");

// 或者把设备上所有 onDemand 块与点位整批刷一遍
int n = await engine.TriggerOnDemandReadAsync("IM-01");
```

## 5.5 想深一层（可选）：一拍的语义

> 心智模型。调度器以一个 50ms 节拍运转：

- **分桶**：同设备、相同 `intervalMs` 的点/块归一个桶，一个桶一轮内读完；不同间隔各走各的节拍。
  每设备仍只有一条轮询线程，实际周期误差 ≤ 一个节拍（50ms）。
- **自动分组**：同一桶里按 (unitId, area) 把地址连续的点合并成一次请求；组内跨度超上限
  （寄存器 `groupLimitRegisters`=125 / 位 `groupLimitBits`=2000）自动切成多次请求，背靠背同一拍读完。
  散点越多、越连续，IO 越省。
- **一次通讯读 10 个点 vs 10 次请求**：合并后只花一次往返的 IO 开销，9 次请求的建立、排队、
  等待全省了。这就是"自动分组"存在的全部意义。
- **`once`**：Start 后读一次，第一次没读到会一直重试到成功一次为止，成功后不再读；
  所以 `once` 不能配 `intervalMs`（间隔无意义，写了报错）。

## 5.6 常见坑与最佳实践

🔴 反模式：间隔写 <50ms。加载直接报错。
✅ 正确写法：≥50ms；现场一般 500–1000ms 起步，真有高频需求再往下压（第 9 章 9.2.5 有调优建议）。

🔴 反模式：以为 `mode="onDemand"` 也会被轮询。
✅ 正确写法：onDemand 完全不进轮询计划，只靠 `TriggerReadAsync` / `TriggerOnDemandReadAsync`
手动驱动（第 8 章调试门面还会再见到）。

🔴 反模式：`mode="once"` 还配 `intervalMs`。加载报错。
✅ 正确写法：once = 启动读一次直到成功，间隔无意义，别写。

🔴 反模式：把 30 和 35 两个地址放进一个 Block，中间留洞。加载报"块内点位地址必须连续"。
✅ 正确写法：块内地址必须连续（空洞 ≤ `Scheduler@ignoreGap`，默认 0）；散点想合并就让自动分组
去干，或者用 `<Slices>` 声明非连续片段（见 `docs/配置XML说明.md`）。

## 5.7 小结

- 节奏写在点/块自己身上：`intervalMs` ≥50ms、`mode` = auto / onDemand / once。
- 散点自动分组：连续地址合并一次通讯；寄存器 ≤125 / 位 ≤2000，超限自动切分、同一拍读完。
- `<Block>` 显式声明"一次请求读一整段"；块内地址必须连续、点位不得覆盖块的决定权。
- onDemand 不进轮询，只手动触发；once 启动读一次直到成功。
- IO 效率口诀：一次通讯读 10 个点，永远比 10 次请求划算。

下一步：第 6 章。调度出来的值要"喂"给界面 / 落盘 / 推送——事件总线怎么接。

# 第 6 章 事件总线与宿主集成

## 6.1 从"报警列表少了三条"说起

你把值变化事件接到一个很慢的回调里——比如每次收到值都写一次数据库：

```csharp
// 慢逻辑，却放在最不该放的地方……
engine.Bus.Subscribe<PointValueChangedEvent>(env =>
    database.Save(env.Body.DeviceId, env.Body.PointId, env.Body.Value));  // 每次值变化都落库
```

结果：界面卡顿、报警列表漏记，你还找不到原因。问题多半出在两处——把"慢逻辑"放进了会拖累采集的
投递路径，或者队列满了被静默丢弃。

这一章讲事件总线：能订哪些事件、两种投递模式怎么选、队列满了怎么办、订阅者写崩了会不会带崩框架，
以及"框架 vs 宿主"的职责边界。

## 6.2 为什么用"事件"而不是"回调地狱"——行为层理由

1. **解耦**：框架只发事件，宿主按需订阅。值变化、报警、写审计、退避、错误，全走一条总线。
2. **慢消费者不拖累采集**：默认 `Queued` 投递，慢逻辑在自己的队列里慢慢消费，采集线程不受影响。
3. **订阅者异常不影响框架**：你的回调抛异常，总线吞掉并计数，采集照常。
4. **丢弃可见**：队列满按策略丢弃时计数会涨，**绝不静默丢弃**——审计/报警漏记你一定能发现。

## 6.3 先认识术语

- **IEventBus（事件总线）**：引擎的 `engine.Bus`。框架只管 Emit，宿主只管 Subscribe。
- **IEventEnvelope（事件信封）**：`{Seq, Time, Body}`——`Seq` 是全局单调序号（可检测丢事件）、
  `Time` 是投递时间、`Body` 是事件本体。
- **DeliveryMode（投递模式）**：`Inline`（发出方线程同步跑，无队列）/ `Queued`（默认，进订阅者专属
  有界队列异步投递）。
- **OverflowPolicy（溢出策略）**：`DropOldest`（默认，挤掉最旧的）/ `DropNewest`（丢弃新入队的）/
  `Wait`（阻塞发出方直到有空位，永不丢弃）。
- **SubscribeBatch（批量订阅）**：攒满 N 条或超过 T 时间回调一次，适合高频值事件。
- **ISubscription（订阅句柄）**：`Delivered` / `Dropped` / `Faults` / `IsActive` / `Dispose()`（退订）。

## 6.4 动手做：把 IM-01 的值、报警、审计、错误都接上

### 6.4.1 可订阅事件家族（一张表）

| 家族 | 事件 | 什么时候发 |
|---|---|---|
| 值变化 | `PointValueChangedEvent` | 值或质量相对缓存变化时（高频，用批量订阅） |
| 报警三态 | `AlarmRaisedEvent` / `AlarmClearedEvent` / `AlarmAcknowledgedEvent` | 激活 / 恢复 / 确认（都实现 `IAlarmEvent`） |
| 写审计 | `PointWrittenEvent` | 所有写操作，无论成败（第 4 章提过） |
| 退避 | `BackoffEnteredEvent` / `BackoffRecoveredEvent` | 进入 / 恢复退避（第 8 章） |
| 错误族 | `TimeoutError` / `ProtocolError` / `LinkError` / `DeviceExceptionError` / `DecodeError` / `PolicyError` / `ConfigError` / `WriteIndeterminateError` | 各类运行时故障（都实现 `IErrorEvent`） |

### 6.4.2 一个订阅接全 IM-01

```csharp
using SuperSampler.Abstractions.Events;
using SuperSampler.Abstractions.Errors;   // IErrorEvent / 错误事件类型

// 值变化：高频，用批量订阅（攒 200 条或 500ms 回调一次，批量刷界面）
using var values = engine.Bus.SubscribeBatch<PointValueChangedEvent>(batch =>
{
    foreach (var env in batch)
        RenderPoint(env.Body.DeviceId, env.Body.PointId, env.Body.Value);
}, maxBatchSize: 200, maxBatchDelay: TimeSpan.FromMilliseconds(500));

// 报警三态：按基接口 IAlarmEvent 一条订阅收齐（第 7 章细讲）
using var alarms = engine.Bus.Subscribe<IAlarmEvent>(env =>
    Console.WriteLine($"[报警] {env.Body.GetType().Name} {env.Body.DeviceId}/{env.Body.PointId} {env.Body.AlarmId}"));

// 错误族：按基接口 IErrorEvent 一次订阅收齐（信封信封协变，能收到全部 8 种错误）
using var errors = engine.Bus.Subscribe<IErrorEvent>(env =>
    Console.WriteLine($"[{env.Seq}] {env.Body.GetType().Name}: {env.Body.Info.Code}"));

// 写审计：低频不可丢，用 Wait + 大队列
using var audit = engine.Bus.Subscribe<PointWrittenEvent>(env => FlushAudit(env.Body),
    mode: DeliveryMode.Queued, overflow: OverflowPolicy.Wait, queueCapacity: 8192);

// 订阅者异常观察点：别让框架"吞掉"你不知道
engine.Bus.HandlerFaulted += ex => Log.Error($"事件订阅者异常：{ex}");
```

> 需要细分时再按具体事件类型单独订阅（比如 `Subscribe<TimeoutError>`）。一次订阅基接口收齐一族
> 是默认姿势。

### 6.4.3 Inline vs Queued 怎么选

| 模式 | 行为 | 适用 |
|---|---|---|
| `Inline` | 在**发出方线程**同步执行，没有队列，`queueCapacity` / `overflow` 被忽略 | 计数、更新最近值缓存这类微秒级逻辑 |
| `Queued`（默认） | 进入该订阅者**专属有界队列**，异步投递；慢消费者不拖累采集线程 | 落盘、写屏、网络推送等慢逻辑 |

> 高频类别（值变化每秒成百上千条）记得 `SubscribeBatch` 攒批；低频类别（报警、写审计）用普通
> `Subscribe` 即可。`SubscribeBatch` 依赖队列攒批，传 `Inline` 一律按 `Queued` 处理。

## 6.5 想深一层（可选）：队列的脾气

> 心智模型。Queued 订阅 = 一条独立后台线程 + 有界队列，FIFO 保序。

- 慢消费者把队列塞满 → 触发溢出策略。`DropOldest` 挤掉最旧的一条再放新事件；`DropNewest` 丢新保旧；
  `Wait` 阻塞发出方直到有空位——**只允许配给审计、报警这类低频且不可丢的类别**。
- `ISubscription.Dropped` 计入"队列满按策略丢弃"和"退订 / 总线停止时队列里未投递的条目"两类，
  绝不静默丢弃。宿主可以定期看 `engine.Bus.Metrics`（`TotalEmitted` / `TotalDropped` / `TotalFaults`）
  做健康看板。
- 订阅者处理时抛异常：总线吞掉并计数（`Faults` + 触发 `HandlerFaulted`），采集线程不受影响。

## 6.6 框架 vs 宿主：职责边界

| 责任 | 归属 |
|---|---|
| 按配置采集、解析成工程值、报警评估、写回、事件发布、断线退避、数据质量模型 | **框架** |
| 显示（界面 / 曲线 / 报警列表） | **宿主** |
| 权限（认证 / 登录 / 角色授权） | **宿主**（框架只用操作者姓名做写审计记账，不拦写入） |
| 存储（历史库 / 报表 / 导出） | **宿主** |
| 领域语义（报警码 → 中文、单位换算后的业务含义、陈旧阈值） | **宿主** |

> 一句话（第 1 章 1.2 就说过）：**框架给你可信的数据与事件，业务判断留给宿主。**

## 6.7 常见坑与最佳实践

🔴 反模式：把写数据库这种慢逻辑做成 Inline 订阅，界面卡顿。
✅ 正确写法：慢逻辑一律 Queued（默认就是）；Inline 只放计数、置标志这类微秒级操作。

🔴 反模式：高频值事件用普通 Subscribe，每事件一次回调，被每秒几百条淹没。
✅ 正确写法：`SubscribeBatch` 攒批；低频类别（报警、写审计）才用普通 Subscribe。

🔴 反模式：订阅者抛异常不管，以为会影响框架。
✅ 正确写法：框架会吞掉并计数（`Faults` + `HandlerFaulted`）；订阅 `HandlerFaulted` 做告警和统计。

🔴 反模式：不监控 `Dropped`，审计 / 报警漏记而不自知。
✅ 正确写法：审计、报警类用 `OverflowPolicy.Wait`（不可丢）；定期看 `Metrics.TotalDropped`。

## 6.8 小结

- 事件家族：值 / 报警 / 写审计 / 退避 / 错误；错误族按 `IErrorEvent`、报警族按 `IAlarmEvent`
  一次订阅收齐。
- Inline（快、无队列）vs Queued（慢、有界队列，默认）；慢逻辑永远 Queued。
- 溢出策略：DropOldest（默认）/ DropNewest / Wait（低频不可丢用 Wait）。
- 订阅者异常不影响框架（`HandlerFaulted` 观察）；丢弃计数可见，别让审计漏记。
- 职责边界：框架给可信数据与事件，界面 / 权限 / 存储 / 业务语义归宿主。

下一步：第 7 章。值变化事件之外，框架还内置了一个报警引擎。

# 第 7 章 报警引擎

## 7.1 从"温度飙到 85 度竟然没报警"说起

你的模具温度上限是 80℃，有一天涨到 85℃ 却什么都没发生：

```xml
<!-- 你可能是这么配的…… -->
<Point id="barrel.temp" address="30" dataType="int16">
  <Scale factor="0.1"/>
  <!-- 少了 <Alarm/>，当然永远不会有报警事件 -->
</Point>
```

查了半天：报警根本没配，或者配了但 `delayMs` 太长、`deadband` 设成了负、报警类型用错（把 `high`
配成了 `low`）。或者反过来——温度在 79.9 和 80.1 之间抖，报警一会儿亮一会儿灭，操作员快疯了。

这一章把报警引擎的五个类型、三个关键参数、三态事件、人工确认全部讲清。

## 7.2 为什么报警"不是比较一下就完"——行为层理由

1. **要防抖**：直接比较会让报警在限值附近抖动。`delayMs`（持续多久才触发）+ `deadband`（恢复死区）
   一起解决它。
2. **要锁存**：有些报警恢复后也不能悄悄消失，必须人工确认——`latch` + `ackRequired`。
3. **语义归宿主**：框架只报 `(deviceId, pointId, alarmId)`；"报警码 1 = 油温过高"是宿主查表，
   框架不做业务解释。
4. **坏值不参与评估**：质量非 Good 的值不触发报警，避免"读了个坏值就误报"。

## 7.3 先认识术语

- **报警类型**：`high`（值 > 上限）/ `highHigh`（更高一级上限）/ `low`（值 < 下限）/
  `lowLow`（更低一级下限）/ `digital`（布尔点位为激活电平）。
- **limit（限值）**：high 类就是上限值（按**工程值**比较，缩放之后）；digital 类决定触发电平
  （`limit="1"` = true 触发，`limit="0"` = false 触发，不写 = 非零即触发）。
- **delayMs（延时）**：持续超过该毫秒数才触发（防抖，滤掉毛刺）。
- **deadband（死区）**：恢复回差（上限 27、死区 0.3：升到 27 触发，降到 26.7 以下才恢复）。
- **latch / ackRequired（锁存 / 需确认）**：锁存报警即使条件恢复也不自动清除，必须人工确认。
- **AlarmClasses（报警等级）**：`AlarmClass@id` 是 `Alarm@priority` 的可选集合（`name/color/sound`
  是宿主渲染用的，框架不消费）。
- **报警键**：`Alarm@id`；点位未写 `Alarm@id` 时 = `pointId#type`。

## 7.5 想深一层（可选）：报警的状态机

> 心智模型。每个报警键（`Alarm@id` 或 `pointId#type`）有一个状态：

```
正常 →(条件满足且过 delayMs)→ 激活(Raised)
激活 →(条件恢复且过 deadband)→ 清除(Cleared)
激活+latch → 只能人工确认(Acknowledged)后才能清除 / 回到可重触发
```

- 同一点位可配多条报警（如 high + highHigh），限值关系必须 `lowLow < low < high < highHigh`——
  配反了加载期直接报错（第 2 章 2.1 那类"一次报全"）。
- `digital` 触发电平：`limit="1"` = true（非零）触发、`limit="0"` = false（零）触发、不写 = 非零触发。
- 坏值（质量非 Good）不参与评估。

## 7.6 常见坑与最佳实践

🔴 反模式：把"报警码 1 = 油温过高"这种映射写在框架里。
✅ 正确写法：框架只报 `(deviceId, pointId, alarmId)`；映射、颜色、弹窗、联动停机全部宿主查表做
（第 6 章 6.6 职责边界）。

🔴 反模式：用 raw 值配 limit（比如限值写成 2600，实际温度上限是 260）。
✅ 正确写法：报警比较发生在工程值上（缩放之后），限值写 260；不确定就先 `GetValueDetail` 看工程值。

🔴 反模式：忘了 `ackRequired` 报警要人工确认，等着它自己消失。
✅ 正确写法：`latch` + `ackRequired` 的报警必须 `AcknowledgeAlarmAsync`；`NotPending` 不是失败

🔴 反模式：限值关系配反（high = 90、highHigh = 80）。
✅ 正确写法：`lowLow < low < high < highHigh`，让加载器替你兜底（配反直接报错）。

- 五类报警：high / highHigh / low / lowLow / digital；限值比较按工程值。

# 第 8 章 断线韧性

## 8.1 从"网线一拔界面就卡死"说起

现场有人踢到网线，你的程序立刻：界面假死、请求堆积、重连循环把 CPU 打满……甚至崩溃。
如果你自己写过重连循环，你一定见过这种"断线轮询风暴"：

```csharp
// 反模式画风：失败后 10ms 重试一次，越断越猛
while (true)
{
    try { ReadRegisters(); }
    catch { Thread.Sleep(10); }   // 链路断了还高频猛打，CPU 100%、请求堆积
}
```

SuperSampler 的做法是**两级退避**：断了就按档位逐步拉长重试间隔，成功一次立刻归零；断线期间
不崩不卡，质量自动回退，恢复全程可见。

## 8.2 为什么退避能"自己恢复"——行为层理由

1. **失败分级**：读超时 → 设备级退避（只有那台从站停）；IO 失败 → 链路级退避（整条链路停）。
2. **自动升级**：同链路所有从站都退避 → 自动升级为链路级，说明问题在链路而不是单个设备。
3. **显式延迟队列**：`delays="300,1000,3000,10000,30000"` 逐档等待、用尽循环末值、成功一次归零。
4. **断线不崩不卡**：退避期间不发请求；点位质量置 Offline/Bad；恢复后自动回到正常轮询。
5. **看得见**：退避事件 + 质量 + `GetValueAge`，宿主管控屏想怎么显示怎么显示。

## 8.3 先认识术语

- **两级退避（two-level backoff）**：设备级（单个从站）/ 链路级（整条链路）。
- **Global/Reconnect（退避配置段）**：`enabled` / `delays` / `manualRetry` / `offlineQuality`。
- **BackoffEnteredEvent / BackoffRecoveredEvent**：进入 / 恢复退避事件。
- **RetryDeviceAsync / RetryLinkAsync**：运维层手动重试（打断退避、立即试一次）。
- **TCP keepalive**：探测假死连接（空闲 10s 开始探测、每 3s 一次、连续 3 次不通由系统关闭连接）。
- **协议异常不计入退避**：设备明确回异常码说明设备在回话，既不进退避也不重置队列。

## 8.4 动手做：让断线恢复"看得见"

### 8.4.1 默认就有退避，不用写代码

退避是**默认开启**的，用下面这段配置（也就是默认值，写不写行为一样）：

```xml
<Global>
  <Reconnect enabled="true" delays="300,1000,3000,10000,30000"
             manualRetry="true" offlineQuality="offline"/>
</Global>
```

行为规则（第 2 章 2.3 的"声明即生效"在这里最明显）：

- 失败**一次**即进队列，按 `delays` 逐档等待；队列用完后一直用最后一个值循环；
  任何一次成功通讯即归零。
- 触发分级：**读超时 → 设备级**；**IO 失败 / 链路断开 → 链路级**；
  **同链路全部从站都在设备级退避 → 自动升级为链路级**（防"半开假死"的第二道防线）。
- 退避期间该目标所有点位按 `offlineQuality`（默认 `offline`）置质量，值按
  `Global/Quality@onCommErrorValue`（默认 `keepLast`）保留旧值。

### 8.4.2 订阅退避事件

```csharp
using SuperSampler.Abstractions.Events;

// 进入退避：每次失败（重试后仍失败也一样）发一条，宿主可直接显示"下次重试时间"
using var bo = engine.Bus.Subscribe<BackoffEnteredEvent>(env =>
{
    var e = env.Body;   // Scope(Device/Link) / Attempt / DelayMs / NextRetryAt / ReasonCode
    Console.WriteLine($"[退避] {e.Scope} {e.DeviceId ?? e.TransportId} 第{e.Attempt}档 "
                    + $"等{e.DelayMs}ms，下次重试 {e.NextRetryAt:HH:mm:ss}（{e.ReasonCode}）");
});

// 恢复退避：一次成功通讯即触发
using var br = engine.Bus.Subscribe<BackoffRecoveredEvent>(env =>
    Console.WriteLine($"[恢复] {env.Body.DeviceId ?? env.Body.TransportId} 已回到正常轮询"));
```

> `ReasonCode` 三值：`MODBUS.TIMEOUT`（设备级）/ `MODBUS.LINK`（链路级）/
> `SS.BACKOFF.ALL_DEVICES`（同链路全部从站退避 → 升级为链路级）。

### 8.4.3 现场"立刻再试一次"（运维动作，不受门禁）

```csharp
// 立即重试单台设备：打断其设备级退避，按其轮询计划采集一次
var retry = await engine.RetryDeviceAsync("IM-01");
if (retry.Outcome == ManualRetryOutcome.Succeeded)
    Console.WriteLine("设备已重试成功，退避归零");

// 立即重试整条链路：清空退避，关闭连接并立即重连
var r2 = await engine.RetryLinkAsync("im01-net");
```

- 成功一次 → 该设备与所属链路的退避队列**一起归零**；失败 → 退避继续（档位加深一档）。
- `manualRetry="false"` 时返回 `NotSupported`，**不发任何通讯**。

> `SamplerEngine` 还实现了调试门面 `IModbusDebugTool`（共 7 个方法，三类能力）：
> 运维层手动重试（`RetryDeviceAsync` / `RetryLinkAsync`，上面刚讲过）、物理层原始读写
> （`RawReadAsync` / `RawWriteAsync`，按 `(area, address)` 直读直写、不做解析，受
> `Diagnostics@allowRawAccess` 门禁、默认关）、语义层手动触发（`TriggerReadAsync` /
> `TriggerBlockReadAsync` / `TriggerOnDemandReadAsync`，走完整解析管道、结果写缓存）。
> 所有调试请求与轮询共用同一条通道队列，**排队执行、不插队**——不会破坏轮询顺序。

### 8.4.4 演示步骤（对着玩具从站）

1. 起玩具从站 + 宿主，订阅退避事件，正常读值。
2. Ctrl+C 停掉玩具从站 → 观察：退避事件档位逐档加深、间隔拉长；`GetValueDetail` 质量变 `Offline`；
   `GetValue` 返回 `nullText`（"--"）。
3. 重新起玩具从站 → 观察到恢复事件，值回到 `Good`。全程程序没崩、界面没卡。

## 8.5 想深一层（可选）：退避队列的心智模型

> 不懂也能用。这是行为规则，不是实现。

- **失败一次即进队列**，不设"连续 N 次"门槛；按 `delays` 逐档等待，队列用尽循环末值；
  任何一次成功通讯即归零，回到正常轮询节奏。
- **两级 + 升级**：读超时 → 设备级；IO 失败 / 链路断开 → 链路级（关连接 → 按队列等待 → 惰性重连）；
  同链路全部从站都设备级 → 自动升级链路级。协议异常（设备明确回异常码）不计入退避。
- **keepalive 是"假死"的第一道防线**：TCP / RTU-over-TCP 通道自动设置，空闲 10s 探测、每 3s 一次、
  3 次不通由系统关闭连接 → 之后的写报 IO 错 → 自动升级为链路级退避。
- 调试请求与轮询**共用同一条通道队列，排队执行、不插队**——手动重试不会破坏轮询顺序。

## 8.6 常见坑与最佳实践

🔴 反模式：自己写 `while(true) { try { read } catch { Thread.Sleep(100) } }` 重连循环。
✅ 正确写法：交给框架的退避。框架管重试节奏，你只订阅 `BackoffEnteredEvent` /
`BackoffRecoveredEvent` 展示状态（8.4.2）。

🔴 反模式：断线期间每 100ms 轮询一遍，造成"断线轮询风暴"。
✅ 正确写法：退避期间框架**不发任何请求**；要"立刻试一次"就用 `RetryDeviceAsync` / `RetryLinkAsync`
（运维动作）。

🔴 反模式：断线时界面上还显示旧值当"实时值"。
✅ 正确写法：`GetValue` 对非 Good 返回 `nullText`（第 1、3 章说过）；要"显示旧值 + 标注过期"
用 `GetValueDetail` 自己画。

🔴 反模式：把 `manualRetry` 关掉却不告诉现场。
✅ 正确写法：`manualRetry="false"` 时 `Retry*` 返回 `NotSupported`（不发通讯）；按需开，别误关。

## 8.7 小结

- 两级退避：读超时 → 设备级、IO 失败 → 链路级、同链路全从站退避 → 自动升级链路级、成功一次归零。
- 显式延迟队列 `delays`（默认 300,1000,3000,10000,30000）：逐档等待、用尽循环末值。
- TCP keepalive：空闲 10s / 每 3s / 3 次判死，防半开假死连接。
- 断线期间不崩不卡：不发请求、质量回退（Offline）、`GetValue` 返回 nullText；恢复自动可见。
- 手动重试：`RetryDeviceAsync` / `RetryLinkAsync`（运维动作，不受门禁）；成功一次退避归零。

### 9.2.1 Jint 脚本解码（第 3 章解码管道的补充）

`Scale` 不够用的时候（查表、组合、取模、复杂换算），可以在点位里写一段 JS 做解码。
脚本在解码管道中的位置（回看第 3 章 3.5）：

```
寄存器 → swap → 类型 → [raw / rawValue] → 脚本 → 工程值（不再叠加 Scale）
```

```xml
<Point id="mix" name="混料比例" address="40" dataType="uint16">
  <!-- 脚本返回的值就是工程值；rawValue 是缩放前的原始值 -->
  <Script><![CDATA[
    // 超过 1000 按 1% 折算，否则算 0——Scale 表达不了这种分段规则
    if (rawValue > 1000) return rawValue * 0.01;
    return 0;
  ]]></Script>
</Point>
```

- 可用绑定：`raw`（该点位声明字长的寄存器数组）/ `rawValue`（按 dataType/swap 解出的缩放前值）/
  `P('id')`（取同点表其它点位值，只认好值）/ `T('key')` / `device` / `point` / `timestamp`。
- 语言是 **ES5.1**（没有箭头函数 / `let` / `const`）；默认超时 50ms；失败按 `onError="markBad"`
  置 Bad + 错误事件；**绝不阻塞采集线程**（超时/异常只影响该点位本轮的值）。
- 回指第 3 章 3.5：脚本产出即工程值，不再叠加 Scale——否则会二次换算。

### 9.2.2 单 DLL 打包（第 2 章"接入方式"的交付形态）

开发时用项目引用；**交付现场**时把 Core + Abstractions + Drivers.Modbus + Jint 四合一打成
**一个 DLL**：

```bash
dotnet restore src/SuperSampler.Core/SuperSampler.Core.csproj
dotnet build  src/SuperSampler.Core/SuperSampler.Core.csproj -c Release -p:EnableILRepack=true
# 产物：src/SuperSampler.Core/bin/Release/net46/merged/SuperSampler.Core.dll
```

- 宿主只放这一个文件（Jint 已内嵌），建议放 `lib/` 目录 + csproj 相对 HintPath 引用。
- 运行时随附的其它资产是你的运行文件：HostConfig 配置 XML、i18n 文案文件等。
- 升级：替换 DLL → 重编宿主 → 回归读值 / 写值 / 报警 / 事件 / 断线。门面签名若变，编译期立刻暴露。
- 注意：net46 程序集**无法被 .NET Core 直接引用**（需 ≥ net461，当前未验证）——.NET Core 宿主先别想。

### 9.2.3 模板 Templates（第 2 章配置的"复用"）

现场几十台同型号设备，重复配置写到手软？用模板抽公共部分：

```xml
<DeviceTemplates>
  <DeviceTemplate id="inj-base" transport="im01-net" unitId="1" swap="word"/>
</DeviceTemplates>
<Devices>
  <!-- 实例属性覆盖模板；模板独有的子元素（Scale/Format/Alarm/Retry）会垫入实例 -->
  <Device id="IM-01" name="1号注塑机" template="inj-base" pointSet="IM01_Points"/>
  <Device id="IM-02" name="2号注塑机" template="inj-base" unitId="2" pointSet="IM02_Points"/>
</Devices>
```

点位模板同理：`Point@template` 引用 `<PointTemplates>` 里定义的点位模板。

### 9.2.4 多从站 / 串口拓扑（第 2 章"链路管怎么连"的扩展）

- **一条链路挂多个从站**：同 `transport`、不同 `unitId`（TCP 走 IP:端口 + 从站号）。
- **一条串口链路挂多个设备**：同一个 `portName`（物理同一条串口总线），用 `unitId` 区分；
  RTU 串口参数（`baudRate` / `parity` / `stopBits` / `handshake` 等）配在 Transport 上。

```xml
<Transports>
  <!-- 一个串口链路，下面两个设备共用这个端口 -->
  <Transport id="rs485" variant="rtu" portName="COM3" baudRate="9600"
             dataBits="8" parity="even" stopBits="one"/>
</Transports>
<Devices>
  <Device id="IM-01" name="1#从站" transport="rs485" unitId="1" pointSet="IM01_Points"/>
  <Device id="IM-02" name="2#从站" transport="rs485" unitId="2" pointSet="IM02_Points"/>
</Devices>
```

- **同一 `(transport, unitId)` 不得被两个启用的 Device 声明**——会重复轮询同一从站，加载报错。
- RTU 同链路从站共享带宽：`requestTimeoutMs` 与轮询间隔按整条链路总通讯量配；
  各设备点位数量差异大时用不同 `intervalMs` 分桶控制节奏（第 5 章 5.3 的分桶）。

### 9.2.5 性能调优建议（第 5 章的实战补充）

- **间隔**：默认 1000ms；真有高频需求再压到 500ms，别低于 50ms 节拍（写了报错）。
- **分组**：尽量让同区地址连续，自动分组会把它们合并成一次通讯；别为了"美观"拆开。
- **块**：一段一段读比散点读更省 IO，用 `<Block>` 显式声明窗口（第 5 章 5.4 例 2）。
- **事件**：高频值事件用 `SubscribeBatch` 攒批；审计 / 报警用 `OverflowPolicy.Wait` 保不丢（第 6 章）。
- 记住第 5 章那句：**一次通讯读 10 个点 vs 10 次请求，差的不是一点半点。**

## A.2 保存为 `toy_slave.py`

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""
注塑机 IM-01 玩具从站（Modbus TCP）——配合《SuperSampler 新手到精通教程》使用。
跑起来：  python toy_slave.py
有真设备：把教程里所有 host / port / unitId 换成你的。

数据区（0 基地址，标准 Modbus 大端）：
  1x 离散输入   offset  3    报警（bool）
  3x 输入寄存器 offset  1    报警码（0无 / 1油温过高 / 2模具超温 / 4射胶异常）
                 offset 30    料筒1段温度（int16, ×0.1 → raw 2200 ≈ 220.0℃）
                 offset 35    模具实际温度（int16, ×0.1）
                 offset 10    射胶压力（float32, swap="none" 时读到 22.0，第3章演示用）
  4x 保持寄存器 offset  1    目标产量（uint16, 可写）
                 offset  2    料筒1段设定（int16, ×0.1, 可写；实际温度向它靠拢）
                 offset  3    报警注入（教程附加：写 1 触发报警码+离散报警，写 0 复位，第7章用）
                 offset 10    配方名（ASCII 12 字节 "RX-88"，第3章演示用）
"""
import threading
import time

from pymodbus.datastore import (ModbusSequentialDataBlock, ModbusSlaveContext,
                                ModbusServerContext)
from pymodbus.server import StartTcpServer

# 三块数据区（0 基地址）
di = ModbusSequentialDataBlock(0, [False] * 16)   # 离散输入 1x
ir = ModbusSequentialDataBlock(0, [0] * 64)       # 输入寄存器 3x
hr = ModbusSequentialDataBlock(0, [0] * 64)       # 保持寄存器 4x

ir.setValues(1, [0])                 # 报警码 = 0（无报警）
ir.setValues(30, [2200])             # 料筒1段温度 = 220.0℃
ir.setValues(35, [1800])             # 模具实际温度 = 180.0℃
ir.setValues(10, [16816]); ir.setValues(11, [0])   # 22.0f 大端 = 0x41B0 0x0000
hr.setValues(1, [100])               # 目标产量
hr.setValues(2, [2300])              # 料筒1段设定 = 230.0℃
hr.setValues(10, [0x5258, 0x2D38, 0x3800, 0, 0, 0])  # "RX-88" ASCII 补零

context = ModbusServerContext(
    slaves=ModbusSlaveContext(di=di, ir=ir, hr=hr, zero_mode=True), single=True)


def drift_loop():
    """模拟工艺：料筒温度每 0.2s 向设定值靠拢 1 个 raw（第 4/7 章写设定后观察用）。"""
    while True:
        setp = hr.getValues(2, count=1)[0]
        temp = ir.getValues(30, count=1)[0]
        if temp < setp:
            ir.setValues(30, [min(setp, temp + 1)])
        elif temp > setp:
            ir.setValues(30, [max(setp, temp - 1)])
        time.sleep(0.2)


def inject_loop():
    """HR offset 3 被写 1/0 时联动报警码 + 离散报警（第 7 章演示用，真设备没有这个口）。"""
    last = 0
    while True:
        cur = hr.getValues(3, count=1)[0]
        if cur != last:
            ir.setValues(1, [1 if cur else 0])
            di.setValues(3, [bool(cur)])
            last = cur
        time.sleep(0.1)


threading.Thread(target=drift_loop, daemon=True).start()
threading.Thread(target=inject_loop, daemon=True).start()

print("IM-01 玩具从站已启动：127.0.0.1:1502，unitId=1（Ctrl+C 退出）")
StartTcpServer(context=context, address=("127.0.0.1", 1502))
```

|---|---|

| 第 3 章 | 加 `pressure`（float32 swap="none"，读 22.0）与 `recipe`（string，读 "RX-88"）两个点 |
