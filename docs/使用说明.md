## 1. 架构与职责边界

SuperSampler 是**库，不是应用**。它做且只做一件事：**按 XML 配置采集**——把现场设备的寄存器
按点位表读出来、解析成工程值、做报警评估、支持写回，并以事件的形式把一切可观测的变化推给宿主。
除此之外的一切都由上位机（宿主）负责。

### 1.1 职责分工

| 责任 | 归属 | 说明 |
|---|---|---|
| 按配置采集（调度 / 轮询 / 块读） | **框架** | 毫秒级间隔、地址自动分组、块读合并 |
| 解析成工程值（类型 / 字序 / 缩放 / 脚本） | **框架** | 13 种数据类型、4 种字序、Scale、Jint 脚本 |
| 报警评估（类型 / delay / deadband / latch） | **框架** | 产出报警三态事件与可确认状态 |
| 写回（范围 / 类型容量 / 可写区 / 回读校验） | **框架** | 四态结果 + 审计事件 |
| 事件发布（值 / 报警 / 写 / 退避 / 错误） | **框架** | 进程内事件总线 |
| 断线退避策略 | **框架** | 设备级 / 链路级两级退避 + TCP keepalive |
| 数据质量模型（值 + 质量 + 时间戳） | **框架** | `PointValue` 三元组，质量四态 |
| 显示（界面 / 曲线 / 报警列表） | **宿主** | 框架只给值，不管怎么画 |
| 权限（认证 / 登录 / 角色授权） | **宿主** | 角色授权体系属宿主职责；框架只用操作者姓名做写审计记账，不拦截写入 |
| 存储（历史库 / 报表 / 导出） | **宿主** | 框架不给存储 |
| 命令与操作时序（点动 / 联动 / 配方下发） | **宿主** | 用 `SetValueAsync` 逐条驱动 |
| 在线状态查询 | **宿主** | 用质量 / `GetValueAge` / 退避事件自行判定 |
| 领域语义（报警码 → 中文、单位换算后的业务含义） | **宿主** | 见 1.2 |

### 1.2 框架不解释数据语义

框架产出的是 `PointValue`：`{值, 质量, 时间戳}` 三元组。**值是什么含义，框架不负责。**

- 报警引擎触发 `AlarmRaisedEvent`，事件里是 `(deviceId, pointId, alarmId)`；**alarmId 对应哪句中文、
  什么颜色、要不要弹窗、联动什么动作，由宿主查表**。框架只校验报警 id 的引用是否悬空。
- 一个点位「多久没刷新算陈旧」取决于工艺（温度 1s、配方 1h），框架**不做陈旧判定**，
  只通过 `GetValueAge` 把「距上次成功采集的时长」交给你，阈值由宿主定。
- 报警 `AlarmClass` 配置里的 `name` / `color` / `sound` 是给宿主渲染用的，框架不消费
  （加载器只会把「未被消费」记入 Warnings 提醒你注意）。

> 一句话：**框架给你可信的数据与事件，业务判断留给宿主。**

## 2. 环境与构建

### 2.1 目标框架

- 目标框架 **.NET Framework 4.6**，兼容 4.6 ~ 4.8。
- **零外部运行时依赖**：唯一第三方组件是 Jint 脚本引擎（供 `script` 解码用），且可以 ILRepack 内嵌成单 DLL
  （见第 3.2 / 12 章）。
- `Directory.Build.props` 引入了 `Microsoft.NETFramework.ReferenceAssemblies` 包——它只在**构建期**使用
  （没有装 VS 的机器也能用 `dotnet` CLI 编译 net46），不会随产物发布。

### 2.2 常用命令

```bash
# 还原 + 构建整个解决方案（Debug / Release 均可）
dotnet build SuperSampler.sln -c Debug

# 跑全部测试：单元 1257 例 + 集成 175 例 = 1432 例，应全绿
dotnet test SuperSampler.sln

# 构建示例宿主
dotnet build samples/InjectionLineMonitor/InjectionLineMonitor.csproj -c Debug

# 单 DLL 打包（详见第 3.2 / 12 章）
dotnet build src/SuperSampler.Core/SuperSampler.Core.csproj -c Release -p:EnableILRepack=true
```

### 2.3 测试现状

- `tests/SuperSampler.UnitTests`：1257 例单测，覆盖配置加载校验、编解码矩阵、事件总线、退避、报警等。
- `tests/SuperSampler.IntegrationTests`：175 例集成测试，跑在**复杂桩（25 从站 / 1029 点）+ 可编程断路器**的真链路上，
  断路器可注入 refuse / silent / drop / delay / badcrc 等 7 种故障形态，验证断线韧性。
- 8 小时长稳跑测已验证：内存无泄漏。

## 3. 接入方式

框架支持两种接入方式，按你是否要维护框架源码来选。

### 3.1 方式一：项目引用（开发 / 调试 / 跟源码）

直接引用引擎工程（示例宿主 `samples/InjectionLineMonitor` 就是这么做的）：

```xml
<!-- 宿主工程 csproj 里 -->
<ItemGroup>
  <ProjectReference Include="..\..\src\SuperSampler.Core\SuperSampler.Core.csproj" />
</ItemGroup>
```

- **适用场景**：你持有框架源码仓库；要调试框架行为；要修改或扩展编解码 / 驱动 / 调度；希望框架升级时
  跟着源码走、能用 IDE 直接跳到框架实现。
- **注意**：宿主工程需面向 .NET Framework 4.6+（或依赖构建期的 ReferenceAssemblies 包）。

**升级流程**：
1. `git pull` 拉取新版本框架源码；
2. 重新 `dotnet build` 宿主工程；
3. 按编译错误逐个适配破坏性变更；跑一遍 `dotnet test` 确认框架自身全绿；
4. 回归宿主的关键路径（读值 / 写值 / 报警 / 断线恢复）。

### 3.2 方式二：单 DLL（交付 / 现场 / 黑盒集成）

把 Core + Abstractions + Drivers.Modbus + Jint 四合一打成**一个 DLL** 交付：

```bash
dotnet build src/SuperSampler.Core/SuperSampler.Core.csproj -c Release -p:EnableILRepack=true
# 产物：src/SuperSampler.Core/bin/Release/net46/merged/SuperSampler.Core.dll
```

- **适用场景**：把框架当黑盒交付给现场；不暴露源码；宿主与框架分别独立维护、独立升级；
  集成方不需要关心框架内部有哪几个程序集。
- **lib 目录约定**：建议宿主工程里建一个 `lib/` 目录存放该 DLL，csproj 用相对 HintPath 引用：

```xml
<ItemGroup>
  <Reference Include="SuperSampler.Core">
    <HintPath>lib\SuperSampler.Core.dll</HintPath>
    <Private>true</Private>
  </Reference>
</ItemGroup>
```

- **运行时随附文件清单**：单 DLL 模式下，框架本身只需要 `SuperSampler.Core.dll` 这一个文件
  （Jint 已内嵌）。其余需要随宿主部署的是**你自己的运行资产**：`HostConfig` 配置 XML、
  i18n 文案文件、以及配置里引用的任何外部文件——这些不是框架 DLL 的依赖，但运行时必不可少。

**升级流程**：把新版的 `merged/SuperSampler.Core.dll` 替换进宿主的 `lib/` → 重新构建宿主 → 回归测试
（重点：读值 / 写值 / 报警 / 事件订阅——若框架升级改了门面签名，宿主会在编译期立刻暴露）。

## 4. 引擎生命周期

### 4.1 总览

```
SamplerConfigLoader.LoadFromXml(path)     ① 加载 + 两阶段校验
        │
        ▼
SamplerConfiguration（零错误才产出）
        │
        ▼
new SamplerEngine(config)                 ② 构造（未通过加载校验的配置无法构造）
        │
        ▼
engine.Bus.Subscribe(...)                 ③ 先订阅
        │
        ▼
engine.Start()                            ④ 启动调度
        │
        ▼
GetValue / GetValueDetail / SetValueAsync / AcknowledgeAlarmAsync ...   ⑤ 日常使用
        │
        ▼
engine.Stop()                             ⑥ 停止（Stop 后不可再 Start）
engine.Dispose()                          ⑦ 释放（可选，using 时自动）
```

### 4.2 第一步：加载与校验（`SamplerConfigLoader.LoadFromXml`）

```csharp
using SuperSampler.Core.Config;

SamplerConfiguration config;
try
{
    config = SamplerConfigLoader.LoadFromXml(@"C:\cfg\host.xml");
}
catch (ConfigValidationException ex)
{
    // 两阶段校验，一次报全所有配置矛盾：
    // ex.Errors    —— 硬错误，全部修完才能通过
    // ex.Warnings  —— 可接受但不推荐的点（如被配置了但框架不消费的字段）
    foreach (var error in ex.Errors)
        Console.WriteLine("  · " + error);
    throw;
}
```

- 加载是**两阶段**的：第一阶段做结构解析，第二阶段做全量语义校验（id 悬空、地址越界、类型与长度不匹配、
  写/报警配置矛盾等）。**所有错误一次性收集进 `ConfigValidationException.Errors`**，不会只报第一条。
- 只有**零错误**才返回配置对象；校验失败的配置永远不会有 `SamplerEngine` 实例。
- 加载器把「相对路径按配置文件所在目录解析」：i18n 文案文件等外部文件放在配置同目录即可；
  脚本不是外部文件，直接写在配置的 `<Script>` 元素内（没有外部脚本文件）。

### 4.3 第二步：构造 `SamplerEngine`

```csharp
using SuperSampler.Core.Runtime;

using var engine = new SamplerEngine(config);
```

- `SamplerEngine` 实现了门面接口 `IDeviceManager` / `IModbusDebugTool`，同时实现 `IDisposable`。
- 手工 new 一个 `SamplerConfiguration`（未经加载器校验）无法通过引擎构造——这是「零错误才实例化」的
  兜底：未通过加载校验的配置不能实例化引擎。
- 引擎构造后**不会立即开始通讯**，你还有机会先订阅事件。

### 4.4 第三步：先订阅、后 Start

```csharp
// 引擎一启动就发事件，晚订阅会漏掉第一批（第一批采集可能就在启动后几毫秒发生）
using var sub = engine.Bus.Subscribe<PointValueChangedEvent>(e =>
    Console.WriteLine($"[{e.DeviceId}/{e.PointId}] {e.Value}"));
```

事件订阅的完整说明见第 7 章。

### 4.5 第四步：Start / Stop / Dispose

```csharp
engine.Start();   // 启动调度：按配置的 intervalMs 开始轮询所有使能设备

// ... 日常读写 ...

engine.Stop();    // 停止调度器，释放轮询线程；Stop 是幂等友好的（见下）
engine.Dispose(); // 释放事件总线等资源；using 语句会自动调用
```

生命周期边界（务必遵守）：

- **先订阅后 Start**：这是硬性要求，理由见 4.4。
- **`Stop` 后不可再 `Start`**：引擎是一次性对象。`Stop` 释放了调度器，重新 `Start` 是不受支持的；
  宿主如需重新运行，请**重建一个 `SamplerEngine`**（配置对象可复用）。
- `Dispose` 是安全的收尾：即使没有手动 `Stop`，`using` 块结束也会自动停止。
- 引擎在宿主进程里是**长期存活**的对象：建议在应用启动时创建、应用退出时销毁，
  不要为单次读取反复创建/销毁引擎。

## 5. 读值

门面读值有三个方法，都是**只读实时缓存、绝不发起通讯**，可以放心高频调用（每秒几十次没问题）。

| 方法 | 返回 | 语义 |
|---|---|---|
| `GetValue(deviceId, pointId)` | `string` | 解析后的**显示字符串**（缩放、枚举映射、前后缀、i18n 均已完成）。质量非 Good 一律返回全局 `nullText`，**绝不把旧值当好值显示**。 |
| `GetValueDetail(deviceId, pointId)` | `PointValue` | 完整三元组 `{值, 质量, 时间戳}`。需要按质量分支处理（置灰、判联锁）的逻辑用这个。 |
| `GetValueAge(deviceId, pointId)` | `TimeSpan?` | 距该点位**上次成功采集**的时长；`null` = 从未成功采集过。框架不做陈旧判定，阈值由宿主定。 |

### 5.1 质量四态（`PointQuality`）

语义对齐 OPC UA：**值永远伴随质量与时间戳，三者不可分割**。

| 质量 | 含义 | 典型触发 |
|---|---|---|
| `Good` | 数据可信 | 正常采集、解码成功 |
| `Uncertain` | 数据可疑，值可能仍可用但需谨慎 | 越界、换算异常（NaN 等） |
| `Bad` | 数据不可用 | 解析失败、被策略丢弃 |
| `Offline` | 链路或设备离线 | 通讯失败、退避中 |

- 每个 `PointValue` 还带 `Reason`（质量非 Good 时的坏值原因，i18n key；Good 时为 `null`），
  宿主用 `Reason` 做界面提示，不要自己猜原因。
- 非 Good 时 `GetValue` 返回 `nullText`（配置 `Global@nullText`），`GetValueDetail` 仍然给你
  `{值, 质量, 时间戳, Reason}` 全量信息——界面上既要显示旧值又要标注「过期」，用 `GetValueDetail` 自己画。

#### 5.1.1 框架产出的原因码速查表

`Reason` 是稳定的 i18n key，框架实际会产出下列常见值（宿主做界面提示 / 联锁可直接按码查表，不要依赖具体语言文案）：

| Reason 码 | 场景 |
|---|---|
| `ss.quality.offline` | 链路或设备离线 / 退避中（对应质量 `Offline`） |
| `ss.reason.comm` | 通讯失败（超时 / 链路断开，质量降级） |
| `ss.reason.shortFrame` | 回帧过短 / 被截断（协议层） |
| `ss.reason.decode` | 原始值解码失败（类型 / 字序 / 字符串 / BCD） |
| `ss.reason.nan` / `ss.reason.infinite` | 换算出 NaN / 无穷（质量 `Uncertain`） |
| `ss.reason.calculate` | 计算点求值失败（缺值等） |
| `ss.reason.scriptTimeout` / `ss.reason.scriptError` / `ss.reason.scriptNull` | 脚本解码超时 / 抛异常 / 返回空 |
| `ss.reason.belowMin` / `ss.reason.aboveMax` | 写值低于 `Write@min` / 高于 `Write@max`（写被拒） |
| `ss.reason.notWritable` | 点位不可写（写被拒） |
| `ss.reason.encode` | 写入编码失败 |
| `ss.reason.notInCache` / `ss.reason.noChannel` / `ss.reason.notSupported` | 缓存无值 / 无可用通道 / 不支持的操作 |

### 5.2 使用姿势

```csharp
// 显示字符串（质量非 Good → "--"，由 nullText 决定）
string text = engine.GetValue("PLC-1", "temp");

// 按质量分支（判联锁、置灰用这个）
PointValue detail = engine.GetValueDetail("PLC-1", "temp");
if (detail.IsGood)
{
    // 用 TryGetValue 做类型安全取值，类型不符返回 false，不抛异常
    if (detail.TryGetValue<double>(out var temp))
        CheckInterlock(temp);
}
else
{
    Console.WriteLine($"质量 {detail.Quality}，原因 {detail.Reason}");
}

// 数据年龄（宿主自己定「多久算陈旧」）
TimeSpan? age = engine.GetValueAge("PLC-1", "temp");
if (age.HasValue && age.Value > TimeSpan.FromSeconds(5))
    ShowStaleBadge(detail);
```

> 注意：`deviceId` / `pointId` 不存在时这三个方法抛 `KeyNotFoundException`——配置写错应尽早暴露，
> 不要吞掉。

## 6. 写操作

### 6.1 两种重载

```csharp
// 不带操作者：以框架内置身份 Local 记审计（适合接入宿主登录前的场景）
Task<WriteResult> SetValueAsync(string deviceId, string pointId, object? value,
                                CancellationToken ct = default);

// 带操作者：审计按该用户记账（接入宿主登录后请用这个；角色授权由宿主自行完成）
Task<WriteResult> SetValueAsync(string deviceId, string pointId, object? value,
                                ActingUser user, CancellationToken ct = default);
```

`ActingUser(Name, RoleId)` 是宿主**认证后**的操作者。框架用它**只做审计记账**（写审计事件里的
`User` 字段），**不做角色授权**——写管道不校验权限，`Write@permission` 当前未实现（配置了会按
`unsupportedPolicy` 记入加载告警）。**角色授权体系属宿主职责**：需要按角色拦截写入时，请宿主在调用
`SetValueAsync` 前自行判断。

写入走**完整写管道**：

```
范围/类型容量校验 → 可写区校验 → 编码 → 下发 →（verify=true 时）回读校验
```

> 说明：**联锁与角色权限当前未实现**，不参与管道校验（按放行处理）。范围校验用的是 `Write@min` / `Write@max`；
> 回读校验见 6.3。

业务失败用**结果对象**表达，不抛异常；只有编程错误（null 参数、未知 id）才抛异常。

### 6.2 四态结果（`WriteOutcome`）与处置建议

| Outcome | 含义 | 处置建议 |
|---|---|---|
| `Succeeded` | 写入成功（verify=true 时已通过回读校验） | 正常。若 `VerifyMismatch` 置位，见 6.3 |
| `Failed` | 明确失败：设备拒绝或通讯错误 | **可安全重试**（重试不会产生副作用） |
| `Indeterminate` | 不确定：超时或应答异常，写入**可能已生效** | **绝不自动重试**。须回读确认后再决定下一步 |
| `Rejected` | 被拒绝：范围（`Write@min`/`max`）/ 类型容量 / 可写区等校验未通过，**未发出任何通讯** | 提示操作者，重试也没用，先改条件 |

```csharp
var result = await engine.SetValueAsync("PLC-1", "pressure", 150, operatorUser);
switch (result.Outcome)
{
    case WriteOutcome.Succeeded:
        if (result.VerifyMismatch)
            ShowNotice($"实际值 {result.Readback} 与写入值不同（设备可能自行钳位）");
        break;
    case WriteOutcome.Failed:
        break; // 可重试
    case WriteOutcome.Indeterminate:
        // 绝不自动重试；读回现场值确认是否已生效
        var check = await engine.GetValueDetail("PLC-1", "pressure");
        break;
    case WriteOutcome.Rejected:
        break; // 提示操作者，不重试
}
```

### 6.3 `VerifyMismatch`：回读不一致只提示，不重试

当点位配置 `verify="true"` 且通讯成功时，框架会回读校验。如果设备应答成功、但回读值与写入值不一致
（典型如设备自行钳位到量程内），结果对象会置位 `VerifyMismatch`，但 `Outcome` 仍为 `Succeeded`——
因为**通讯确实成功**。宿主应在界面明确提示「实际值 X 与写入值不同」，并且**不要自动重试**
（重试不会改变设备的钳位行为）。

### 6.4 类型强转建议

写值请按点位 `dataType` 给对应 .NET 类型：数值点给 `int` / `long` / `double`，字符串点给 `string`。
把界面输入原样以字符串传给数值点，框架可能做隐式转换——但**字符串 → 数值会丢精度或失败**，
最好在宿主侧把界面输入按 `dataType` 强转成数值后再写入。

## 7. 事件订阅

### 7.1 订阅 API

```csharp
ISubscription Subscribe<TEvent>(
    Action<IEventEnvelope<TEvent>> handler,
    DeliveryMode mode = DeliveryMode.Queued,
    OverflowPolicy overflow = OverflowPolicy.DropOldest,
    int? queueCapacity = null) where TEvent : IEvent;
```

- 信封 `IEventEnvelope<TEvent>` 携带 `Seq`（全局单调序号，宿主可据此检测事件丢失）、`Time`（投递时间，UTC）、`Body`（事件本体）。
- 返回 `ISubscription` 句柄：`Dispose()` 即退订；`Delivered` / `Dropped` / `Faults` / `IsActive` 提供可观测计数。

### 7.2 `DeliveryMode`：两种投递模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `Inline` | 在**发出方线程**同步执行。契约：订阅者必须极快（如计数）。没有队列，`queueCapacity` / `overflow` 被忽略 | 计数、更新最近值缓存这类微秒级逻辑 |
| `Queued`（默认） | 进入该订阅者**专属的有界队列**，由泵线程异步投递。慢消费者不拖累采集线程 | 落盘、写屏、网络推送等慢逻辑 |

### 7.3 `OverflowPolicy`：队列满时怎么办

| 策略 | 行为 |
|---|---|
| `DropOldest`（默认） | 挤掉队列里最旧的一条，放入新事件 |
| `DropNewest` | 丢弃正在入队的新事件 |
| `Wait` | 阻塞发出方直到有空位（永不丢弃）——**只允许配给审计、报警这类低频且不可丢的类别** |

丢弃必须可见：`ISubscription.Dropped` 计入「队列满按策略丢弃」与「退订 / 总线停止时队列里未投递的条目」两类，
**绝不静默丢弃**——静默丢弃会让宿主的审计 / 报警漏记而不自知。

### 7.4 可订阅事件清单

| 类别 | 事件 | 内容 |
|---|---|---|
| 值变化 | `PointValueChangedEvent` | `(DeviceId, PointId, Value)` 新值三元组 |
| 报警三态 | `AlarmRaisedEvent` / `AlarmClearedEvent` / `AlarmAcknowledgedEvent` | 报警激活 / 恢复 / 确认（三态见第 8 章） |
| 写审计 | `PointWrittenEvent` | 写操作审计（所有写操作无论成败都发）：`DeviceId / PointId / Value / User / Outcome / Message`，外加 `ElapsedMs`（写管道耗时）、`DidReadback`（是否发起过回读）、`Readback`（回读值 `PointValue?`）、`VerifyMismatch`（设备钳位标记）。需要回读值的宿主**直接订阅本事件即可取到**，不必再去 `WriteResult` 里取 |
| 退避 | `BackoffEnteredEvent` / `BackoffRecoveredEvent` | 进入 / 恢复退避（见第 10 章） |
| 错误族 | `TimeoutError` / `ProtocolError` / `LinkError` / `DeviceExceptionError` / `DecodeError` / `PolicyError` / `ConfigError` / `WriteIndeterminateError` | 全部实现 `IErrorEvent` |

### 7.5 一次订阅整个错误族

错误事件都实现基接口 `IErrorEvent`，且信封是协变的——**订阅 `IErrorEvent` 就能收到所有错误事件**：

```csharp
// 一次订阅，覆盖全部错误族（超时 / 协议 / 链路 / 设备异常 / 解码 / 策略 / 配置 / 写不确定）
using var errSub = engine.Bus.Subscribe<IErrorEvent>(env =>
    Console.WriteLine($"[{env.Seq}] {env.Body.GetType().Name}: "
                    + $"{env.Body.Info.Code}（{env.Body.Info.MessageKey}）"));

// 需要细分时，按具体事件类型单独订阅
using var timeoutSub = engine.Bus.Subscribe<TimeoutError>(env =>
    CountTimeout(env.Body.Info));
```

### 7.6 订阅者异常不影响框架

订阅者处理时抛异常，总线**吞掉异常并计数**（`ISubscription.Faults` + 总线 `HandlerFaulted` 事件），
采集线程不受影响。宿主应订阅 `engine.Bus.HandlerFaulted` 做告警与统计。

```csharp
engine.Bus.HandlerFaulted += ex => Log.Error($"事件订阅者异常：{ex}");
```

### 7.7 批量订阅（`SubscribeBatch`，高频值事件的标准用法）

高频类别（如 `PointValueChangedEvent`）用 `SubscribeBatch` 攒批回调，避免每个事件都触发一次订阅者调用：

```csharp
ISubscription SubscribeBatch<TEvent>(
    Action<IReadOnlyList<IEventEnvelope<TEvent>>> handler,
    int maxBatchSize,
    TimeSpan maxBatchDelay,
    DeliveryMode mode = DeliveryMode.Queued,
    OverflowPolicy overflow = OverflowPolicy.DropOldest,
    int? queueCapacity = null) where TEvent : IEvent;
```

- **攒批条件**：攒满 `maxBatchSize` 条，**或**距批首事件超过 `maxBatchDelay` 时间，回调一次（两条件先到先触发）。
- **高频类别按需订阅或批量订阅**：如值变化事件每秒成百上千条，用批量订阅把「每事件一次回调」降为「每批一次」，
  适合落盘、批量刷新界面等场景；低频类别（报警、写审计）用普通 `Subscribe` 即可。
- `SubscribeBatch` 依赖队列攒批，`DeliveryMode.Inline` 对它没有意义——传 `Inline` 一律按 `Queued` 处理。

```csharp
// 攒 200 条或 500ms 回调一次，批量刷界面
using var batch = engine.Bus.SubscribeBatch<PointValueChangedEvent>(list =>
{
    foreach (var env in list)
        RenderPoint(env.Body.DeviceId, env.Body.PointId, env.Body.Value);
}, maxBatchSize: 200, maxBatchDelay: TimeSpan.FromMilliseconds(500));
```

## 8. 报警

### 8.1 五种类型与三个关键参数

配置里用 `<Alarm>` 声明报警（节点写法见第 11 章与 `配置XML说明.md`）：

| 类型 | 触发条件 |
|---|---|
| `high` | 值 > 上限 |
| `highHigh` | 值 > 更高一级的上限（同一点位可配多级报警，限值关系：`lowLow < low < high < highHigh`） |
| `low` | 值 < 下限 |
| `lowLow` | 值 < 更低一级的下限（双低限） |
| `digital` | 布尔点位为激活电平（判定规则见下） |

> `digital` 的触发电平由 `Alarm@limit` 决定：`limit="1"` 表示点位值为 true（或非零）时触发，
> `limit="0"` 表示值为 false（或零）时触发；不写 `limit` 时按值为 true（或非零）触发。

三个关键参数：

- **`delayMs`**：持续超过该毫秒数才触发（防抖，滤掉毛刺）。
- **`deadband`**：恢复死区（如上限 27、死区 0.3：升到 27 触发，降到 26.7 以下才恢复），避免在限值附近抖动。
- **`latch` / `ackRequired`**：锁存报警即使条件恢复也不会自动清除，必须人工确认（`AcknowledgeAlarmAsync`）。

### 8.2 报警三态事件

| 事件 | 触发时机 |
|---|---|
| `AlarmRaisedEvent` | 条件满足且过 delay → 报警激活 |
| `AlarmClearedEvent` | 条件恢复（过 deadband）；或 ack 后重触发条件清除 |
| `AlarmAcknowledgedEvent` | 人工确认：`AcknowledgeAlarmAsync` 成功 |

确认接口：

```csharp
Task<AlarmAckResult> AcknowledgeAlarmAsync(string deviceId, string pointId, string alarmId,
                                           CancellationToken ct = default);
Task<AlarmAckResult> AcknowledgeAlarmAsync(string deviceId, string pointId, string alarmId,
                                           ActingUser user, CancellationToken ct = default);
```

- `alarmId` 与 `AlarmRaisedEvent.AlarmId` 一致（点位未写 `Alarm@id` 时为 `"pointId#type"`）。
- `AlarmAckOutcome`：`Acknowledged`（确认已记录，并发出 `AlarmAcknowledgedEvent`）/ `NotPending`
  （当前没有可确认状态：从未触发过，或该 alarmId 不在该点位的报警配置里——**这不是失败**，只是无事可确认）。

### 8.3 报警码 → 中文，留给宿主

框架只报 `(deviceId, pointId, alarmId)`，**不解释 alarmId 的业务含义**：

- 报警文案（`Alarm@message` 引用的 i18n key）、颜色、声音、是否联动停机，全由宿主渲染与决策。
- 配置里的 `AlarmClass@name` / `color` / `sound` 框架**不消费**，仅校验 id 引用是否悬空
  （加载器会把这些记入 Warnings）。
- 需要「报警列表 / 历史」的宿主，请自行订阅三态事件累积，或从 `Alarm` 配置 + 当前点位值自行查询——
  框架**不提供报警查询接口**（见第 13 章）。

## 9. 错误处理

框架的错误处理遵循一个统一原则：**配置错误在加载期一次报全；业务失败用结果对象表达；运行时故障用事件广播。**

### 9.1 配置错误：`ConfigValidationException`

- 加载期（`LoadFromXml`）发现的所有配置矛盾一次性收进 `ConfigValidationException.Errors`，
  宿主打印全部错误后直接拒绝启动（示例宿主的做法）。
- `Warnings` 是「可接受但不推荐」的点（如配了框架不消费的字段），宿主可打印提醒，不阻断启动。
- 只有零错误才可能走到 `SamplerEngine` 构造；未通过加载校验的配置（如手工 new 的）无法实例化引擎（见第 4.3 章）。

### 9.2 写错误：结果对象

写入失败**不抛异常**，返回 `WriteResult(Outcome, Error, Readback, VerifyMismatch)`。四态与处置见第 6.2 章。
`Error` 是 `ErrorInfo?`：失败或不确定时携带错误信息；成功与拒绝时可能为 null（拒绝原因见日志 / 事件）。

### 9.3 读错误：质量降级

通讯失败、解码异常不会抛异常，而是把点位质量降级（`Uncertain` / `Bad` / `Offline`），
`GetValue` 返回 `nullText`，`GetValueDetail` 可看到完整原因（`Reason` i18n key）。界面据此置灰，不显示假数据。

### 9.4 运行时错误：错误事件族

运行时故障以事件广播，并按可恢复性分类：

| 接口 | 语义 | 具体事件 |
|---|---|---|
| `ITransientError` | 瞬时错误，可重试 | `TimeoutError`、`ProtocolError` |
| `ILinkError` | 链路级错误 | `LinkError` |
| `IPermanentError` | 永久错误，重试无意义 | `DeviceExceptionError`、`DecodeError`、`ConfigError` |
| `IIndeterminateError` | 不确定错误 | `WriteIndeterminateError` |
| `IPolicyError` | 策略错误 | `PolicyError` |

宿主按 `IErrorEvent` 基接口一次订阅全族（见 7.5），按需再细分处理。

### 9.5 `ErrorInfo` 结构（错误事件的载荷）

每个错误事件的 `Info` 都是 `ErrorInfo`，字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | `string` | **稳定错误码**（如 `MODBUS.EXCEPTION.02`）。**必须跨版本稳定**，外部系统 / 脚本 / 报警规则会引用它 |
| `MessageKey` | `string` | i18n key，由宿主本地化成具体语言的句子；框架不产出用户可见文案 |
| `Category` | `EventCategory` | 事件类别（进入事件总线的路由依据） |
| `Level` | `EventLevel` | 事件级别 |
| `Source` | `ErrorSource` | 错误发生在哪一层，宿主据此判断找谁排查 |
| `Context` | `ErrorContext` | 结构化上下文 |

`Source`（`ErrorSource`）分层：`Transport`（连接 / 串口 / IO）、`Protocol`（CRC / 帧长 / 事务号）、
`Device`（设备语义 / 异常码 / 拒绝写入）、`Codec`（解码层）、`Policy`（预算 / 队列 / 重连次数）、
`Config`（配置层）。

`Context`（`ErrorContext`）回答「哪里出错、第几次、花了多久」：`DeviceId / TransportId / UnitId / PointId /
Area / Address / FunctionCode / Attempt / MaxAttempts / ElapsedMs / ConsecutiveFailures / CorrelationId /
TxFrame / RxFrame`，字段全部可选，按实际可用性填充；单行诊断摘要用 `Context.ToString()`（仅供日志，用户可见
文本一律走 `MessageKey` 本地化）。

**分类不在 `ErrorInfo` 里**：错误按标记接口分类（可重试 / 需重连 / 永久 / 不确定 / 策略），见 9.4 的接口表——
分类由错误事件类型唯一确定，宿主用 `ErrorClasses.Classify(env.Body)` 即可拿到 `ErrorClass`。

## 10. 断线与恢复

框架的断线韧性由**两级退避** + **TCP keepalive** + **手动重试**组成，断线期间不崩不卡，
质量回退与恢复全程可见。

### 10.1 两级退避语义

| 退避级别 | 触发条件 | 作用域 | 说明 |
|---|---|---|---|
| **设备级** | 读超时（`requestTimeoutMs`） | 单个设备（从站） | 该设备暂停轮询，按退避档位延迟后重试 |
| **链路级** | IO 失败、链路断开 | 一条链路上所有设备 | 整链路退避，避免对断开的物理链路空轮询 |
| **升级到链路级** | 同链路**全部从站**都进入设备级退避 | 整条链路 | 说明问题在链路而非单个设备，自动升级 |

- 退避队列是 **`Global/Reconnect@delays` 显式延迟队列**（默认 `"300,1000,3000,10000,30000"` 毫秒）：
  失败一次进队列，按序**逐档等待**，队列用完后**一直用最后一个值循环**；**成功一次即归零**，回到正常轮询节奏
  ——无需人工干预。
- 触发分级：**读超时（`requestTimeoutMs`）→ 设备级**退避；**IO 失败 / 链路断开 → 链路级**退避；
  **同链路全部从站都在设备级退避 → 自动升级为链路级**。协议异常不计入退避。

### 10.2 退避事件

```csharp
// 进入退避：每次失败（重试后仍失败也一样）发一条，宿主可直接显示「下次重试时间」
engine.Bus.Subscribe<BackoffEnteredEvent>(env =>
{
    var e = env.Body;
    // e.Scope       —— 退避作用域（Device / Link）
    // e.DeviceId    —— 设备 id（链路级为 null）
    // e.TransportId —— 链路 id
    // e.UnitId      —— 从站号（链路级为 null）
    // e.Attempt     —— 连续第几次失败（1 基）
    // e.DelayMs     —— 本档位等待毫秒数
    // e.NextRetryAt —— 下次重试时刻（UTC）
    // e.ReasonCode  —— MODBUS.TIMEOUT / MODBUS.LINK / SS.BACKOFF.ALL_DEVICES
    Console.WriteLine($"[退避] {e.Scope} {e.DeviceId ?? e.TransportId} 第{e.Attempt}档 "
                    + $"等{e.DelayMs}ms，下次重试 {e.NextRetryAt:HH:mm:ss}（{e.ReasonCode}）");
});

// 恢复退避：一次成功通讯即触发
engine.Bus.Subscribe<BackoffRecoveredEvent>(env =>
    Console.WriteLine($"[恢复] {env.Body.DeviceId ?? env.Body.TransportId} 已回到正常轮询"));
```

### 10.3 调试门面（`IModbusDebugTool`）

`SamplerEngine` 同时实现调试门面 `IModbusDebugTool`，提供三类能力：**运维层手动重试、物理层原始读写、语义层手动触发**。
所有请求与轮询共用同一条通道队列，排队执行，不插队、不破坏轮询顺序。

**① 手动重试（运维层，不受门禁）**

立即打断退避、按计划重试一次（返回 `ManualRetryResult` 表达是否打断了退避）：

```csharp
// 立即重试单个设备（打断其设备级退避，按其轮询计划采集一次）
var r1 = await engine.RetryDeviceAsync("PLC-1");

// 立即重试整条链路（打断链路级退避，关闭连接并立即重连）
var r2 = await engine.RetryLinkAsync("plc");
```

- 语义：成功一次 → 该设备与所属链路的退避队列**一起归零**；失败 → 退避继续（档位加深一档）。
- `Global/Reconnect@manualRetry=false` 时返回 `NotSupported`，不发任何通讯。
- 这是运维动作（现场「立刻再试一次」），不是裸读写，因此**不受 `Diagnostics@allowRawAccess` 门禁**。

**② 原始读写（物理层，受 `Diagnostics@allowRawAccess` 门禁，默认关闭）**

绕过点表语义，按 `(area, address)` 直读直写寄存器 / 线圈，返回**原始值**，不做任何解析（适合排查现场报文）：

```csharp
// 原始读：area 用 ModbusArea 枚举（Coil / DiscreteInput / InputRegister / HoldingRegister）
RawReadResult rr = await engine.RawReadAsync("PLC-1", ModbusArea.HoldingRegister, 0, 10);
// rr.Registers —— 寄存器原始值（位区每个元素为 0/1）；rr.RawBytes —— 大端拼接原始字节，便于人工比对报文

// 原始写：values 以 ushort 列表给出；位区（Coil / DiscreteInput）用 0/1 表示
RawWriteResult rw = await engine.RawWriteAsync("PLC-1", ModbusArea.HoldingRegister, 0,
                                               new ushort[] { 100, 200 });
```

- **`allowRawAccess` 默认关闭**：生产环境必须保持关闭——原始写会绕过写保护。需要开启时在配置
  `Diagnostics@allowRawAccess="true"`；门禁关闭时这些方法直接失败。

**③ 手动触发读取（语义层）**

不走轮询计划、随时手动读一次，结果写入实时缓存并返回：

```csharp
// 触发单个点位读取（走该点的完整解析管道），返回 PointValue
PointValue v = await engine.TriggerReadAsync("PLC-1", "temp");

// 触发整块读取（配置里的 Block），返回读到的寄存器数量
int regs = await engine.TriggerBlockReadAsync("env.air");

// 触发某设备上全部 mode="onDemand" 的块与点位（onDemand 不进轮询计划，只靠这个驱动）
int n = await engine.TriggerOnDemandReadAsync("PLC-1");
```

> `mode="onDemand"` 的点位 / 块**不参与轮询**，只由 `TriggerOnDemandReadAsync`（或 `TriggerReadAsync` /
> `TriggerBlockReadAsync`）手动驱动。onDemand 的配置写法与 `mode` 三值说明见第 11.3 章。

### 10.4 TCP keepalive

TCP 传输默认开启 keepalive：探测死链路，避免「半开连接」导致请求长期挂在 `requestTimeoutMs` 上。
链路故障最终会以链路级退避 + `LinkError` / `TimeoutError` 事件的形式暴露给宿主。

```xml
        </Point>
        <Point id="pressure" name="压力" address="10" dataType="uint16" access="readwrite"/>
      </Points>
    </PointSet>
  </PointSets>
</HostConfig>
```

### 11.2 进阶样例（缩放 / 报警 / 写 / 计算点）

```xml
<PointSet id="Line1_Points">
  <Defaults area="input" dataType="uint16" swap="none"/>

  <Blocks>
    <!-- 块读：一次通讯读整段 -->
    <Block id="env.air" area="input" start="0" count="11" intervalMs="1000" swap="none">
      <!-- 线性缩放 + 高低限报警（带延时 / 死区 / 锁存 + 需确认） -->
      <Point id="env01.roomTemp" name="车间温度" address="0" dataType="int16" unit="℃">
        <Scale factor="0.1"/>
        <Format decimals="1" suffix=" ℃"/>
        <Alarm id="env.highTemp" type="high" limit="27" delayMs="2000" deadband="0.3"
               priority="High" latch="true" ackRequired="true" message="车间温度过高"/>
      </Point>
    </Block>
  </Blocks>

  <Points>
    <!-- 双点缩放 + 钳位 + 可写（范围校验 + 回读校验） -->
    <Point id="moldTemp" name="模具温度" area="input" address="59" dataType="int16"
           access="readwrite" unit="℃">
      <Scale rawLow="0" rawHigh="10000" scaledLow="-50" scaledHigh="200">
        <Clamp mode="low"/>
      </Scale>
      <Format decimals="1" suffix=" ℃"/>
      <Write min="-50" max="200" verify="true"/>
    </Point>

    <!-- 字符串解码 -->
    <Point id="recipeName" name="配方名" area="holding" address="23" dataType="string"
           length="12" intervalMs="5000">
      <String encoding="ascii" trimNull="true"/>
    </Point>

    <!-- 数字量报警（digital） -->
    <Point id="faultAlarm" name="设备报警" area="discrete" address="3" dataType="bool">
      <Alarm id="dev.fault" type="digital" priority="Critical" latch="true" ackRequired="true"
             message="设备报警"/>
    </Point>
  </Points>

  <Calculated>
    <!-- 计算点：不占地址，读取时按表达式实时求值；缺值返回 Bad，不抛异常 -->
    <Point id="tempDev" name="温度偏差" dataType="float64" unit="℃">
      <Expression>P('env01.roomTemp') - P('moldTemp')</Expression>
      <Format decimals="1" suffix=" ℃"/>
    </Point>
  </Calculated>
</PointSet>
```

> 说明：表达式里的 `P('id')` 引用同点表点位，跨设备用限定名 `P('设备id/点位id')`；
> 计算点不占地址、不需要 `intervalMs`（随读取时机求值）。
>
> 注意：`Point@range`、`Write@step` 等字段当前**仅进模型、不产生行为**，写了会按 `HostConfig@unsupportedPolicy`
> （默认 warn）记入加载告警——请勿在配置里使用（未实现段完整清单见第 13 章）。

### 11.3 点 / 块读取模式（`mode` 三值）

`Point@mode` 与 `Block@mode` 控制「何时读」，取值三选一：

| mode | 语义 |
|---|---|
| `auto`（默认） | 参与轮询，按所在桶的 `intervalMs` 周期读取 |
| `onDemand` | **不参与轮询**，只由 `TriggerOnDemandReadAsync`（或 `TriggerReadAsync` / `TriggerBlockReadAsync`）手动触发 |
| `once` | **启动后读一次**，直到成功一次为止；失败按退避节奏重试（退避期间不发请求） |

```xml
<!-- onDemand 示例：配置后不进轮询计划，只等手动触发 -->
<PointSet id="ManualPoints">
  <Points>
    <Point id="batchWeight" name="批次重量" address="60" dataType="uint16" mode="onDemand"/>
  </Points>
</PointSet>
```

```csharp
// 手动触发上面这个 onDemand 点（结果写入实时缓存并返回）
var v = await engine.TriggerReadAsync("PLC-1", "batchWeight");
```

### 11.4 串口（RTU）多从站示例

一条链路可挂**多个串口设备**：它们共享同一个 `Transport`（同一 `portName`，物理上同一串口总线），
用 **`unitId`（从站号）区分**。RTU 串口专属参数（`baudRate` / `parity` / `stopBits` / `handshake` /
`dtr` / `rts` / `readTimeoutMs` / `writeTimeoutMs`）配置在 `Transport` 上：

```xml
<Transports>
  <!-- 一个串口链路，下面两个设备共用这个端口 -->
  <Transport id="rs485" variant="rtu" enabled="true"
             portName="COM3" baudRate="9600" parity="none" stopBits="one"
             dataBits="8" readTimeoutMs="500" writeTimeoutMs="500"/>
</Transports>
<Devices>
  <Device id="PLC-1" name="1#从站" transport="rs485" unitId="1" pointSet="MainPoints"/>
  <Device id="PLC-2" name="2#从站" transport="rs485" unitId="2" pointSet="Line2Points"/>
</Devices>
```

> RTU 同链路从站共享带宽，`requestTimeoutMs` 与轮询间隔要按整条链路的总通讯量来配；
> 各设备点位数量差异大时，用不同 `intervalMs` 分桶控制节奏。

### 11.5 i18n 文案文件格式

i18n 文案文件是**每行一条**的纯文本，格式：`key=value`，`#` 开头为注释；值可带双引号（会被剥掉）。
配置里用 `${KEY}` 引用，加载期做替换：

```
# 本文件由 Global@language 选中
alarm.highTemp=车间温度过高
unit.temp=℃
null.text="--"
```

```xml
<!-- 配置里声明文件 + 语言选择；文件按配置同目录解析 -->
<I18n>
  <Files>
    <File lang="zh_CN" path="zh_CN.txt"/>
    <File lang="en_US" path="en_US.txt"/>
  </Files>
</I18n>
<Global language="zh_CN" fallbackLanguage="zh_CN" nullText="--" ... />
```

- **选中规则**：优先加载 `lang` 与 `Global@language` 匹配的文件；该语言文件缺失时用 `Global@fallbackLanguage`
  兜底；都没有匹配才全部加载。只匹配且磁盘上确实存在的文件才会被加载（缺失静默跳过，`${KEY}` 原样保留）。
- 文案里用 `${KEY}` 引用其它键做组合（如报警消息引用 alarm.* 后拼单位），由 `I18nCatalog` 在加载期替换。

## 12. 单 DLL 打包与升级

### 12.1 打包

```bash
# 先 restore，再以 Release + EnableILRepack=true 构建
dotnet restore src/SuperSampler.Core/SuperSampler.Core.csproj
dotnet build  src/SuperSampler.Core/SuperSampler.Core.csproj -c Release -p:EnableILRepack=true

# 产物
# src/SuperSampler.Core/bin/Release/net46/merged/SuperSampler.Core.dll
```

产物是 **Core + Abstractions + Drivers.Modbus + Jint 四合一**的单个 DLL——合并会把 Jint 内嵌进 DLL，
宿主只需这一个文件。

### 12.2 宿主引用注意事项

- 引用方式见第 3.2 章（`lib/` 目录 + `HintPath`）。
- 宿主目标框架需 **.NET Framework 4.6+**。
- 产物必须仍叫 `SuperSampler.Core.dll`（放在 `merged/` 子目录，不覆盖日常产物）；合并后 Abstractions 的
  事件类型保持 public，宿主才能订阅事件。日常 Release 构建不受影响。

### 12.3 升级

升级流程与第 3.2 章「方式二」的升级流程一致：替换 `lib/` 里的 `SuperSampler.Core.dll` → 重新构建宿主 →
回归读值 / 写值 / 报警 / 事件订阅 / 断线恢复。若新版本改了门面签名，宿主会在编译期立刻暴露。

## 13. 已知边界

框架当前版本**不提供**以下能力，请在设计宿主时留意（后续版本可能补上）：

1. **门面不提供点位元数据枚举**：`IDeviceManager` 没有「列出所有点位 / 点位元数据」的方法。
   宿主如需点位表（名称、类型、单位、地址）用于界面配置，用 `PointRegistry` 自取。
2. **无设备在线状态查询门面**：没有 `IsOnline(deviceId)` 这类接口。宿主用质量（`Offline`）、
   `GetValueAge`、退避事件（`BackoffEnteredEvent` / `BackoffRecoveredEvent`）自行推断并展示。
3. **无报警查询接口**：没有「查当前激活的报警列表」的门面方法。需要报警列表的宿主自行订阅三态事件累积，
   或按 `Alarm` 配置 + 点位当前值自行计算。
4. **`.NET Core / .NET 6` 宿主未验证**：框架程序集面向 net46。.NET Core 只能引用 **>= net461** 的程序集，
   因此 `net46` 程序集无法直接被 .NET Core 宿主引用——若要在 .NET Core 里用，需要先把框架工程改面向
   net461+（当前未验证）。
5. **配置里部分段当前未实现**：以下配置写了**不产生行为**，并会按 `HostConfig@unsupportedPolicy` 处理
   （默认 `warn` 记入加载告警；`error` 加载失败；`ignore` 静默忽略）——**不要按它们的功能期待行为**：

   | 未实现段 / 字段 | 说明 |
   |---|---|
   | `Commands` / `Storage` / `Ui` / `Users` | 命令执行引擎 / 历史存储 / 界面组态 / 用户权限，后续迭代 |
   | `Diagnostics/Trace` / `Diagnostics/Events` / `Diagnostics/Recovery` | 框架内部追踪 / 事件总线策略 / 离线恢复，后续迭代 |
   | `Parsers` | 自定义解码器（归宿主） |
   | 点位 `History` / `Tags` | 历史归档 / 自定义元数据，后续迭代 |
   | `Scale@mode` 非 `linear` | 缩放模式 v1 仅支持 linear |
   | 设备 `generateDiagnostics` / `Simulate` | 自动诊断点 / 仿真模式，后续迭代 |
   | `AlarmClass@name` / `color` / `sound` / `escalateAfterMs` | 等级展示属性由宿主消费，框架未使用 |
   | `Point@range` / `Write@step` / `Write@permission` | 仅进模型，不产生行为（权限未实现，写管道按放行处理） |

   详情与逐字段说明见 `配置XML说明.md` 与源码加载器告警。
